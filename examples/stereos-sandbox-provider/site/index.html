Guide · custom sandboxes

How to add a custom sandbox to Smithers

Any task can run in its own sandbox, and Smithers reaches every sandbox through one provider interface. This guide builds a provider for stereOS microVMs, ships it as @stereos/smithers, and runs it on real hardware.

01 / 03

A workflow renders to tasks

A workflow is React. It renders to a graph of tasks. By default a task runs in the host process, next to your files. Wrap a task in <Sandbox provider={…}> and that task alone runs somewhere else. Isolation is per task, so one workflow mixes both freely.

02 / 03

The provider seam

A provider is the code on the far side of that wrap. Smithers hands it a request as JSON; the provider gets that request into the sandbox, executes there, and returns the result as JSON. Nothing else about the sandbox is Smithers' concern.

03 / 03

What ships, and what you add

Smithers ships first-class providers for these, plus bubblewrap and Docker transports for the local machine. Every other sandbox plugs into the same seam. The rest of this guide builds one.

Eight steps, one package

The worked example is stereOS, a microVM distribution reachable over SSH. Every pane below is a slice of a real file in @stereos/smithers, located by anchor text at build time.

  1. Reach the machine

    The provider does not own the VM lifecycle. mb up boots the mixtape; this script reads the forwarded SSH port off it and opens an admin channel.

[ -n "$port" ] || { echo "could not read an SSH port from: $MB status $VM" >&2; exit 1; }

ssh_admin() {
  ssh -p "$port" -i "$ADMIN_KEY" -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -o LogLevel=ERROR -o IdentitiesOnly=yes admin@127.0.0.1 "$@"

  3. Choose a transport

    A session is one transport to the sandbox. Here it is ssh with a fixed argument list.

    real/stereos-provider.ts@stereos/smithers
    const SSH_HOST = process.env.STEREOS_SSH_HOST ?? "127.0.0.1";
const SSH_PORT = process.env.STEREOS_SSH_PORT ?? "2222";
const SSH_KEY = process.env.STEREOS_SSH_KEY ?? `${HOME}/.config/stereos/ssh-key`;
const SSH_USER = process.env.STEREOS_SSH_USER ?? "agent";

const SSH_ARGS = [
  "-p",
  SSH_PORT,
  "-i",
  SSH_KEY,
  "-o",
  "StrictHostKeyChecking=no",
  "-o",
  "UserKnownHostsFile=/dev/null",
  "-o",
  "LogLevel=ERROR",
  "-o",
  "IdentitiesOnly=yes",
  "-o",
  "ConnectTimeout=10",
  `${SSH_USER}@${SSH_HOST}`,
];
  4. Implement the session

    writeFile, readFile, and exec are the whole seam. destroy is optional: this provider sets cleanup: "keep" because mb up and mb down own the VM.

    real/stereos-provider.ts@stereos/smithers
        const session: SandboxSession = {
      remoteId: `stereos-${request.sandboxId}`,
      async writeFile(path, content) {
        const r = await ssh(`mkdir -p "$(dirname ${q(path)})" && cat > ${q(path)}`, content, {
          signal: request.signal,
          timeoutMs: 30_000,
        });
        if (r.exitCode !== 0) throw new Error(`stereos writeFile ${path} failed: ${r.stderr.trim()}`);
      },
      async readFile(path) {
        const r = await ssh(`cat ${q(path)}`, undefined, { signal: request.signal, timeoutMs: 30_000 });
        if (r.exitCode !== 0) throw new Error(`stereos readFile ${path} failed: ${r.stderr.trim()}`);
        return r.stdout;
      },
      async exec(command, opts) {
        const env = Object.entries(opts.env)
          .map(([k, v]) => `${k}=${q(String(v))}`)
          .join(" ");
        const seconds = Math.max(1, Math.ceil(opts.timeoutMs / 1000));
        return ssh(`cd ${q(opts.cwd)} && env ${env} timeout ${seconds}s sh -c ${q(command)}`, undefined, {
          signal: opts.signal,
          timeoutMs: opts.timeoutMs + 5_000,
        });
      },
    };
  5. Ship the runtime

    The guest needs a launcher and the child workflow. Upload both as the session opens, next to the request file the kit is about to write.

    real/stereos-provider.ts@stereos/smithers
        // Upload the entry runner alongside the request the kit is about to write.
    await session.writeFile(RUNNER_PATH, readFileSync(join(HERE, "guest-runner.sh"), "utf8"));
    await session.writeFile(WORKFLOW_PATH, await buildGuestWorkflow());
    return session;
  6. Launch inside the guest

    The launcher is a shell script. It execs the guest's own Bun on the uploaded bundle.

    real/guest-runner.sh@stereos/smithers
    BUN_PATH="${STEREOS_GUEST_BUN:-/home/agent/.local/bin/bun}"
WORKFLOW_PATH="${STEREOS_GUEST_WORKFLOW:-/home/agent/workspace/.smithers/child-workflow.js}"

[ -x "$BUN_PATH" ] || { echo "guest Bun is missing or not executable: $BUN_PATH" >&2; exit 127; }
[ -r "$WORKFLOW_PATH" ] || { echo "guest child workflow is missing: $WORKFLOW_PATH" >&2; exit 127; }

exec "$BUN_PATH" "$WORKFLOW_PATH"
  7. Write the result

    The guest writes { status, output } to the path Smithers named in the environment. That file becomes the task's output on the host.

    real/child-workflow.tsx@stereos/smithers
    if (import.meta.main) {
  const requestPath = process.env.SMITHERS_SANDBOX_REQUEST_PATH;
  const resultPath = process.env.SMITHERS_SANDBOX_RESULT_PATH;
  if (!requestPath || !resultPath) throw new Error("Smithers sandbox protocol paths are unset");
  const request = await Bun.file(requestPath).json();
  const prompt = z.string().parse(request.input?.prompt);
  const output = await executeGuestWork(prompt, {
    runId: z.string().parse(request.runId),
    sandboxId: z.string().parse(request.sandboxId),
  });
  const result = JSON.stringify({ status: "finished", output });
  await Bun.write(resultPath, result);
  process.stdout.write(`${result}\n`);
  8. Use it

    Point a <Sandbox> at the provider. Nothing else in the workflow changes.

    real/stereos-real.tsx@stereos/smithers
    export default smithers((ctx) => (
  <Workflow name="stereos-real">
    <Sandbox
      id="stereos-vm"
      provider={stereosProvider}
      workflow={childWorkflow}
      input={{ prompt: ctx.input.prompt }}
      output={outputs.result}
      allowNetwork
      reviewDiffs={false}
      timeoutMs={120_000}
      retries={1}
    />
  </Workflow>
));

03 / 03

What is exposed

The gateway's RPC surface is not reachable from the internet. The guard is.

Three workflow ids

hello, pipeline, approval-demo. A workflow id from the request is never forwarded.

Server-chosen input

The guard picks each run's input, so a visitor cannot steer what executes in the guest.

Five RPC methods

Named as literals in guard.ts. No method name from a request reaches the gateway.

2 concurrent, queue of 8

Six starts per IP per ten minutes, counted on the Cloudflare edge IP.

256-bit approval token

Minted at start, compared with timingSafeEqual. Nothing else resolves a gate.

Five minute hard cap

The guard cancels the run and frees its slot. Responses are built field by field.
