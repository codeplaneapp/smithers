Two identity questions decide whether a durable run is safe: which run is this, and which process may mutate it. Smithers answers the first by letting the caller choose the execution id, and the second with a fence that follows the run's recorded owner. Effect's own workflow package answers the first by hashing the flow tag and payload, and Smithers refused that design.

## The caller chooses the execution id

Identity has three sources, consulted in a fixed order. First, the `executionId` the caller named on `execute`. Failing that, the `idempotencyKey` the flow declared, hashed together with the flow tag. Failing both, the ambient `CurrentExecutionIds` source, whose default `derived` hashes the flow tag with the payload's canonical form.

`layerExecutionIds(source)` replaces the third. Replace it when two equal payloads of one flow are not one piece of work in this host, for example one request per user in a coding agent. Callers that name an `executionId` and flows that declare an `idempotencyKey` are unaffected, because both are decided before the source is consulted.

`ExecutionIdRequired` is a defect, not a typed failure. The derived source raises it when the payload has no canonical form, a non-finite number, a lone surrogate, or a cycle, and `derived.mint` dies with it rather than starting a run under a guessed identity. `Flow.executionId(payload)` likewise dies when the payload fails the flow's own payload schema, where `Flow.execute` fails with a typed `SchemaError` instead. Precompute an id with `executionId` only for a payload you have already validated.

## Why the hash-everything join was refused

Upstream derives a run's identity by hashing the flow tag and payload, so two unrelated runs with equal payloads silently join: the second caller's run is the first caller's run, and each reads the other's history as its own. A silent join is worse than a crash, because nothing reports it. In Smithers the caller chooses the id, derivation is opt-in, and a flow with neither an explicit id nor a declared key dies with a structured defect instead of guessing.

## Fenced ownership

Every running run has an owner, an `OwnerId` of host id, process id, and nonce. Every ownership mutation compares all three fields in the same SQL statement as the mutation, so a claim, a heartbeat, an attempt write, or a terminal transition lands only while `flows_runs` still records that owner.

The journal carries the same fence. Attempt lifecycle writes pass the owner and append only while the persisted ownership matches; otherwise they fail `fence_lost`. An owner that is missing or malformed fails `invalid_event` instead: that is a caller contract violation, and reporting it as `fence_lost` would send the caller hunting a race that never happened. `OwnerId` lives in the journal package rather than with the arbitration in `@smthrs/run-store`, because the journal is what it fences.

## The claim protocol

A run row begins pending. Claiming is two phase, `claim` then `activate`, or atomic, `claimAndOwn`. The compare-and-swap reads a complete snapshot: status, owner, and heartbeat together. Partial ownership snapshots are invalid by construction, so a running row always carries both an owner and a heartbeat and every other status carries neither. Terminal rows cannot be reopened.

Compare-and-swap competition is reported as tagged success values such as `FenceLost` and `SnapshotChanged`, separate from the typed error channel, so a caller retries contention without treating corruption as a race.

Attempts sit under the same discipline. An attempt row is addressed by `(runId, stepKeyDigest, attempt)`, and its writes, `put`, `heartbeat`, `finish`, and `patch`, are fenced against the owning running run. `transitionOwned` changes status and optional executable state under one owner fence, with its optional cancellation guard compiled into the same update, so a cancel request cannot land between a check and a terminal write.

## The journal says which answer was used

Arbitration is auditable because the decision is journaled. A refused takeover records `steal-refused-owner-alive` with the evidence that refused it, `lease-fresh` when the lease was still inside the window or `probe` when a supplied liveness check answered for the owner. A takeover records `stolen-and-activated` with its evidence kind. A refusal is journaled once per lease and evidence, not once per sweep tick, because first-writer admission collapses every repeat about an unchanged lease into the one record.

A refusal also defers the run for two heartbeat ticks, doubling per consecutive refusal against the same lease, so the stale-run sweep keeps advancing past recently refused rows instead of re-probing them every tick.

## Zombie owners interrupt themselves

A process killed with SIGKILL leaves its runs marked `running` under a dead owner. A fresh process reclaims them through the lease: the default liveness check counts an owner as alive while its persisted heartbeat is younger than the staleness cutoff, and a steal re-checks the evidence against the row inside the same write, so a claimant that lies about the lease loses the compare-and-swap. The driver's periodic sweep re-drives the stale-running rows a hard-killed owner leaves behind, so neither SIGKILL nor an out-of-memory kill can strand a run.

The reclaimed owner is the zombie, and the fence is what stops it. When the old process wakes and tries to append its next attempt event, the fence fails the write with `fence_lost` and the zombie self-interrupts instead of appending. Ownership is observed at the write, not assumed from the claim.

## Trade-offs and why

Ownership is an arbitration protocol, not a lock manager. Evidence binds to one instant by exact equality, so a probe taken at T is refused by a call made at T+1. A deployment that knows more about liveness, a pid probe on the owner's host or an orchestrator's pod status, supplies its own `isAlive` check and refuses takeovers for longer; a pid names a process only in its own host's namespace, so cross-host recovery relies on the persisted lease.

Clocks get the same distrust. Lease operations refuse a caller clock reading that runs ahead of the store's clock by more than the skew allowance, so a runaway clock can neither steal a fresh owner nor pin a lease past the cutoff. Heartbeats are monotonic: a pulse delayed past a newer one is acknowledged without moving the lease backwards. A run row carries stamps from two clock sources, the caller's `nowMs` on lease operations and the Effect `Clock` on lifecycle transitions, and a composition must give both sources the same reading.

The fence is not a distributed lock. It arbitrates writes to one store, and it does nothing about a process that writes around the store. Ownership is not identity either: one caller may own many runs, and one run changes owners over its life as claims, steals, and recoveries accumulate.
