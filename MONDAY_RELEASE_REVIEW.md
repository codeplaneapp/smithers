# Monday release readiness review

**Recommendation: do not publish the current checkout. A scoped 1.0.0-rc.0 release on `next` on Monday, September 7, is plausible if the correctness fixes land Saturday and Sunday is reserved for validating the final candidate. The evidence does not support calling this stable 1.0 today.**

This review assumes the release already declared by all 49 public package manifests: `1.0.0-rc.0`. It covers repository structure, public APIs, runtime and persistence boundaries, build/cache behavior, migration, security boundaries, tests, documentation, package delivery, and release automation. There are 116 workspace manifests; the release roster is derived through `readWorkspaceManifests`, including the public tooling packages. The private UI and applications are outside the npm roster but remain selected by required gates.

The initial HEAD was `c3734a0118994581a7901bdac56350549f37a347`, with eight pre-existing modified files. Other work continued during this review, including changes to approval records and a new database migration. Results below describe the snapshots actually tested, not one immutable candidate. Source hashes, package inventory, probes, and logs are retained in [the evidence directory](review-evidence/2026-09-04/monday-release-review/). This is a repository-wide readiness assessment with focused code review and executable probes, not a claim that every line or every platform has been exhaustively verified.

The main gap is concrete: two correctness defects, failing integration gates, stale user-facing documentation, and missing final-candidate evidence. Much of the earlier remediation is implemented and well tested. Reopening every historical finding or rewriting the engine is not necessary to close this release gap.

1. **Build cache correctness — reproduced on Node 24.18.0.** In [PackageExec.ts](packages/smithers/build/build-cli/src/PackageExec.ts), the `HostBin` resolution around line 1085 records the name, path, and version-probe output. It does not record executable content. The resulting toolchain identity enters the cache key around line 2799.

   The retained [probe](review-evidence/2026-09-04/monday-release-review/cache-probe.ts) creates a disposable git workspace and an explicitly declared host compiler. The first build writes `first`. The compiler is then replaced with a program that writes `second`, at the same path and still reporting version `1.0.0`. The second build exits zero, reports `hit`, retains exactly the same cache key, and leaves `first` in the output. See [the full receipt](review-evidence/2026-09-04/monday-release-review/cache-probe.json). The probe uses the supported `sandbox: "none"` declaration to isolate cache identity from filesystem confinement; it is not evidence about a Linux sandbox escape.

   Hash the resolved executable content, account for symlink/script resolution and other executable forms, and invalidate existing cache entries with the corrected identity. Check declared module tools and plain shell/PATH execution too; those adjacent cases are an audit requirement, not additional reproduced bugs here. Tests must assert the new output and dispatch count, not just a different displayed version. A separate inherited-environment probe did **not** establish a bug: the arbitrary variable was filtered from the child environment.

2. **Migration locking — two independently reproduced holes.** [Lock.ts](packages/smithers/migrate/src/flow/Lock.ts) constructs the lock path inside the caller-selected report directory (around line 80). [Command.launch](packages/smithers/migrate/src/flow/Command.ts) uses that lock for `apply` (around line 246). Acquiring `report-a/apply.lock` and `report-b/apply.lock` succeeds for the same project. Both runs can still edit the same source tree.

   The initialization race is separate. The exclusive write creates the file before its JSON record is complete. Lines 156–165 treat unreadable JSON as a dead owner and unlink it. A real child process was paused after exclusive creation and before writing its record. While it was alive and holding that file, the production `Lock.acquire` returned success to a contender. The original child then finished writing and also considered itself the owner. This establishes broken mutual exclusion; the review did not intentionally corrupt a migrated project to demonstrate the downstream damage.

   The existing six lock tests pass despite both holes. Retain [the reproduction](review-evidence/2026-09-04/monday-release-review/lock-probe.ts) as regression coverage. Use one lock identity per canonical project, and a protocol that cannot steal an initializing or newly replaced live lock. Verify concurrent stale reclaimers and ownership-safe release as well as the two reproduced schedules. Do not infer process death from a partially written record.

4. **Onboarding documentation is incompatible with the current public API.** [The agent-output tutorial](apps/site/src/content/docs/docs/tutorials/agent-outputs.mdx) around line 207 and [the agent-step example](apps/site/src/content/docs/docs/examples/11-agent-step.mdx) around line 100 still call `Node.andThen(callback)` imported from `@smthrs/plan`. [Node.ts](packages/smithers/flows/plan/src/Node.ts) now requires a Node argument and deliberately throws `invalid_continuation` for that callback form. The intended data-dependent builder is `Node.bindPlanned`.

   A direct source probe confirms the refusal. The actual example programs already use `bindPlanned`, but six generated example pages drift: 11, 16, 17, 18, 20, and 33. Authored tutorials, including time travel, also require edits. `apps/site/public/llms-full.txt` repeats the obsolete snippets. Its own generation check can pass because it faithfully bundles stale Markdown. The 48 package-doc mirror checks pass, which does not cover the separate main-site content.

   `pnpm --dir apps/site run check:docs` fails on generated `versions.json` drift. The installation page currently says Node 22.19.0 “or later,” whereas the CLI requires `^22.19.0 || >=24.11.0`, excluding Node 23 and early Node 24. Update the rendered support statement and independently verify the first-use tutorial against installed packages.

   This review's actual script-target run has now also rebuilt/packed all 49 packages and completed the installed-consumer smoke on **Node 24.18.0 and minimum Node 22.19.0**, both on macOS arm64. The [Node 24 receipt](review-evidence/2026-09-04/monday-release-review/smoke-evidence.json) and [Node 22 receipt](review-evidence/2026-09-04/monday-release-review/smoke-evidence-node22.json) pass and bind to the **same candidate integrity** in [the manifest](review-evidence/2026-09-04/monday-release-review/release-manifest.json). 6. **Repository metadata has independently failing gates.** `check-lockfile-parity.mjs` reports 11 disagreements in `bun.lock`, including the missing private repository-target workspace, the harness parser replacement, and TypeScript 7 runtime upgrades in build-cli and migrate. Peer validation and the single-Effect-version check pass, but neither proves lockfile parity. The changelog check expects 1,396 commits since v0.35.0 while the generated release section records 1,284. Recompute this again after the last release-source commit.

   The actual script-target run and an independent boundary check also reject four undeclared fixture imports: `@smthrs/flow`, `@smthrs/plan`, `@smthrs/flows`, and `@smthrs/sandbox` in the release sandbox fixtures. Declare the correct development dependencies or give those fixtures an explicit, verified installed-consumer boundary. These failures are release blockers under the existing workflow, even though they are small fixes.

7. **Fault isolation is not encoded in the ordinary CI selection.** `FaultSuite` returns an ordinary `Vitest` target, and the CLI package exports it among its targets. The broad workspace CI launched the CLI's `vitest.faults.config.ts` directly while another package's sandbox tests were running. Its process cwd and parent were verified. This disagrees with the comments describing a separate serial-only fault tier; the release workflow subsequently invokes the fault matrix again with `--jobs 1`.

   The review also started a separate CLI fault run based on that documented separation before discovering the overlap. It completed with **41 tests passing across 22 files, zero skips**, in 439 seconds. This is useful functional recovery evidence, but cannot establish isolated resource/soak behavior. Correct selection or enforce exclusive resource scheduling, then run the serial tier alone. This does not establish that every functional fault test is invalid; it establishes that the promised test isolation is absent.

The estimates are planning judgments, not measured implementation times: roughly **3–5 engineer-days of focused work**, with CI and overnight observation running concurrently. With one person, Monday is tight; with two owners for code correctness and release integration, an RC is more plausible.

**Sunday decision rule:** if cache identity, migration exclusion, required CI, the installed first-use path, or candidate identity is still unresolved, postpone publication. Do not turn a red gate green by lowering coverage, deleting a regression, changing the tested tarballs after approval, or relabeling a failed journey as supported. An RC can carry documented limits; it should not carry these reproducible correctness failures.
