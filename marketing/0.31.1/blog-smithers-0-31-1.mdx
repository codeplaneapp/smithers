Smithers 0.31.1 changes what happens when a long-running agent run goes sideways. Before this release, a stalled run waited for a human to notice, an edited workflow file killed your resume with `RESUME_METADATA_MISMATCH`, and a couple of durability bugs could mark work complete that had not actually finished. After this release, a run can carry its own monitor workflow that watches it and heals it, a wedged run can be resumed in place even after you edit the workflow, and the engine no longer claims completion for work that is still pending.

## Why this release exists

0.31.1 is a patch release by version number and a hardening campaign by volume: 163 commits and 993 changed files ([release range](https://github.com/smithersai/smithers/compare/v0.31.0...v0.31.1)), aimed at the failure modes operators hit when they run agents for hours instead of minutes. The headline capability is monitor workflows, but most of the release is fixes: run recovery, resume semantics, and a large batch of child-run durability issues spanning cancellation, approvals, signals, snapshots, and retries.

## Monitor workflows: runs that watch and heal themselves

The biggest addition is first-class monitor workflows ([f04a8d3d](https://github.com/smithersai/smithers/commit/f04a8d3d701156f1c1dcecdd1573668157831bf9)). Drop a `.smithers/monitor/<workflowId>.tsx` file next to a workflow and Smithers will run it alongside that workflow's runs. The monitor observes the live run and can act on what it sees: when a run stalls or a node wedges, it can auto-heal the condition, and when the situation needs a human, it escalates through a durable `HumanTask` instead of failing silently.

This matters for long-running coding agents because the most expensive failure is not a crash, it is a run that quietly stops making progress at hour three of a six-hour job. A crash pages someone. A stall just burns the clock. Monitor workflows turn "someone should keep an eye on that run" from a habit into an artifact that is versioned, testable, and always on.

The passive monitoring surface got sharper too. `smithers claude monitor` previously fired only on discrete bad state transitions. It now also breaks silence on retry churn, when a node keeps cycling through `node-retrying`, and on long quiet stretches in a live run via `run-progress` events ([834f36af](https://github.com/smithersai/smithers/commit/834f36af5aaa657bd7bd2e92ab32e3222e42fd78)). Those are exactly the two shapes of trouble that discrete-transition alerting misses: a run that is failing busily, and a run that is failing by doing nothing.

Finally, watching a run is now a better experience. `smithers monitor <runId>` serves a dedicated steerable live UI for built-in oneshots, and the oneshot and hijack surfaces were unified into a shared `OneshotSurface` component used both standalone and embedded in the Monitor ([c9b5d0e6](https://github.com/smithersai/smithers/commit/c9b5d0e68ac1390b6641f3ae2193acd8286212c2), [f3cd8b32](https://github.com/smithersai/smithers/commit/f3cd8b3293a4c1da3fb3b636dc46c4d420e2d811)). One surface, whether you are steering a fresh oneshot or hijacking a run mid-flight.

## Recover instead of restart: resume and retry fixes

A common operator loop looks like this: a run wedges on a node, you inspect it, you realize the workflow itself needs a small edit, you make the edit, and then the resume dies with `RESUME_METADATA_MISMATCH` because the workflow on disk no longer matches the one the run was started with. Your only option was to fork a fresh run and eat the lost progress.

0.31.1 closes that loop. `retry-task` now accepts `--accept-workflow-change`, which tells the engine to carry the edited workflow forward into the resumed run ([51e57e1a](https://github.com/smithersai/smithers/commit/51e57e1af7d7e1563dcfdfbc08b54a19c865c30b)), and the mismatch error itself now names the flag so you learn about it exactly when you need it ([32b4bc82](https://github.com/smithersai/smithers/commit/32b4bc82aa65a57ee25a702655db14d97beb9725)):

```sh
# The run wedged, you fixed the workflow file. Resume in place:
bunx smithers-orchestrator retry-task <runId> <nodeId> --accept-workflow-change

# Or resume the whole run with the edited workflow:
bunx smithers-orchestrator up --resume <runId> --accept-workflow-change
```

Starting runs got safer at the other end too. `smithers oneshot` now warns when the working copy is dirty and has the agent triage the uncommitted changes before starting on the goal ([19f98b83](https://github.com/smithersai/smithers/commit/19f98b833962c3cbde7f48cd27b208d69021ef93)), instead of letting an agent barrel into a tree that already contains someone else's half-finished work.

## Durability bugs you could not see

Two fixes in this release close bugs whose whole failure mode was invisibility.

The first is in the compute bridge for `<Task deps>`. When a deps child was an async function, the engine could claim the task complete while the callback's work was still pending, including a child run the callback had launched ([aace057c](https://github.com/smithersai/smithers/commit/aace057c44dd1da78be8be14b63abe0247bde484), closes #1415). Downstream nodes would proceed against an empty `{}` payload, everything would report green, and the missing output only surfaced later as confusing behavior far from the cause. The bridge now awaits the callback before claiming completion, so completion means complete.

The second is in jj time-travel. Attempt pointers were recorded as jj change ids, which alias whatever commit the change currently points at. Restoring to a prior attempt could resolve to the change's current commit, meaning `jj restore` was a silent filesystem no-op: the CLI reported a successful revert while not a single byte on disk moved ([765e3e8f](https://github.com/smithersai/smithers/commit/765e3e8f5fd6a2dee54f693422cafd2c6c513762)). Pointers are now pinned to the exact immutable commit id, so revert and timetravel restore real bytes.

Both bugs share a shape: the system reported success while quietly doing less than it claimed. For a durable runtime, those are the worst class of defect, and both are now pinned by tests.

## Subflows harden across the board

Child runs, workflows launched from inside other workflows, got a coordinated hardening pass across a large batch of tracked issues. The batch spans cancel and pause propagation into children, approval ownership so the right run answers the right gate, signal delivery across child waits ([5a57d72f](https://github.com/smithersai/smithers/commit/5a57d72f159d6aa476f70ad1affb06119ab86c1d)), snapshot lineage isolation, rewind-lease hardening ([5e25a63b](https://github.com/smithersai/smithers/commit/5e25a63b06523285e6fe5a24a74b2d7d6ba3f731)), retry and revert semantics for failed child branches ([a746cea5](https://github.com/smithersai/smithers/commit/a746cea52f9d8e89b21cb04eac768028aa06a428)), gateway attribution ([e3bf9279](https://github.com/smithersai/smithers/commit/e3bf9279445455829c0195820521e5da8b7aa2ec)), and run-list visibility for child runs.

You can now also see the tree, not just the root. Gateway RPC, REST, SDK, and MCP surfaces gained typed queries for a run's descendants and direct children, with regenerated contracts and docs ([2d3cc7e0](https://github.com/smithersai/smithers/commit/2d3cc7e0dd200cfca394eec6b8877203df0f5777), #1391). If your orchestration composes workflows out of workflows, this release is the difference between subflows as a demo feature and subflows as a load-bearing one.

## Safer defaults: sandbox loopback and honest evals

Two defaults changed in the direction of "strict where it protects you, permissive where strictness was just friction."

The network sandbox under `allowNetwork: false` used to block everything, including the agent's own local dev server, local Postgres, and unix sockets. Loopback now stays reachable while remote egress remains denied, and when a connection is denied, the error names the `--allow-network` escape hatch instead of leaving the agent to guess ([0f21a17a](https://github.com/smithersai/smithers/commit/0f21a17ad0ccaa92ff63c0e63bf4948e66ba9687)). The point of the sandbox is stopping exfiltration and surprise egress, not breaking `curl localhost:3000`.

Evals got honest about harness deaths. A case that dies with a network, DNS, TLS, OOM, or rate-limit signature is now graded `INCONCLUSIVE` instead of failed, and `smithers eval` exits with code 5 when every red case is inconclusive ([1ecbe647](https://github.com/smithersai/smithers/commit/1ecbe64754911803058c140dacf85c598b76722f)), so CI can tell "the workflow regressed" apart from "the infrastructure had a bad day." Review verdicts learned the same distinction: a reviewer that could not run its verification for an environmental reason now reports `blocked` rather than `approved: false` ([00422450](https://github.com/smithersai/smithers/commit/00422450a8ab03a4c974b80463f4693d6cee671b)), so environment faults stop reading as rejections of your code.

## Right-sizing and authoring discipline

`create-workflow` now right-sizes the request before building anything ([00422450](https://github.com/smithersai/smithers/commit/00422450a8ab03a4c974b80463f4693d6cee671b)). A trivial edit gets routed to a direct change, a well-scoped goal gets routed to `smithers oneshot`, and only work that genuinely needs ordered stages, approvals, or reuse gets a full workflow scaffold. Overbuilt orchestration is its own failure mode, and the builder now refuses to commit it on your behalf.

On the discipline side, a new `eval-driven-development` skill documents the loop for automated repair: classify red cases before acting, ratchet green so fixed cases stay fixed, and circuit-break runaway repair loops ([9a57e799](https://github.com/smithersai/smithers/commit/9a57e79922b374a8115d8c5989fe6a131b779a57)).

## UI groundwork

Two new packages, `packages/ui-core` and `packages/tui-ui`, extract the shared runs domain, run lists, run trees, event frames, health, and the `useRunsListVm`/`useRunInspectorVm` view models, so the terminal UI and the web UI render the same model ([deb0142c](https://github.com/smithersai/smithers/commit/deb0142cdd788051c43395b4194ce12f0b2a773d), [e1fa1f6d](https://github.com/smithersai/smithers/commit/e1fa1f6dd762a6d811e3ba0d39b9a004b1829a1d)). The approval panel also picked up accessibility improvements, loading skeletons, and richer decision feedback ([54851a08](https://github.com/smithersai/smithers/commit/54851a086af58637c09b06297e93f6c1565afec)).

## Upgrade notes

There are no breaking changes in 0.31.1. Two things are worth checking after you upgrade:

- If a resumed run previously failed with `RESUME_METADATA_MISMATCH` after an in-flight workflow edit, re-run it with `retry-task --accept-workflow-change` (or `up --resume --accept-workflow-change`) instead of forking a fresh run.
- If your workflows use `<Task deps>` with async function children, confirm downstream consumers were not silently reading an empty `{}` payload before this release. The compute bridge now awaits the callback before claiming completion, so outputs that were missing will start arriving.

## Get started

Upgrade and point a monitor at a live run:

```sh
bunx smithers-orchestrator update
bunx smithers-orchestrator monitor <runId>
```
