Smithers is the durable runtime layer for long-running coding agents: persisted state, retries, approvals, replay, sandboxes, evals, and observability. Durability only holds if a run survives the boring failures — a closed pipe, a provider session breaking, a gateway that stops answering while it indexes your workflows. 0.33.1 is about exactly those failures.

Before 0.33.1, a `retry-task` could be killed by a SIGPIPE, an approved detached run could refuse to resume, and a mid-chain provider error could hard-fail a run with perfectly good fallback agents configured. After 0.33.1, each of those degrades to something you can pick back up: runs park, retry, or resume instead of dying.

## Why this release exists

0.33.1 is a patch release for operators upgrading from 0.33.0: 20 commits, 55 files changed, +2,186/−188 lines — 13 fixes, 2 features, 3 docs. No new primitives. The work clusters around three failure modes from real long-running runs:

1. **Runs dying or refusing to resume** — `retry-task` killed by a closed pipe, detached runs stuck with a `null` workflow hash.
2. **Fallback chains silently giving up** — session-loss errors that skipped configured fallback agents instead of triggering them.
3. **Gateway UI discovery misbehaving** — `/health` unreachable during discovery, workflows launched by explicit path never registering.

Each section follows the same shape: the failure mode, what changed, and what it means for a run you left unattended overnight.

## Runs stop dying: retry-task detach and resume fixes

**The failure mode.** `retry-task` ran the engine invocation in the foreground with no detach. If the pipe on the other end closed — a terminal going away, a wrapping process exiting — the resulting SIGPIPE killed the run and orphaned its agent children ([#1481](https://github.com/smithersai/smithers/issues/1481)).

**What changed.** The engine invocation behind `retry-task` is now detached, so a closed pipe no longer takes the run down with it.

Two resume paths got the same treatment:

- An **approved detached run with a `null` workflowHash** previously could not resume at all ([#1489](https://github.com/smithersai/smithers/issues/1489)). It now can.
- **`up --resume <runId>` no longer demands a workflow path**, matching its documented help text ([#1475](https://github.com/smithersai/smithers/issues/1475)). The CLI derives the stored workflow from the recorded run, pinned by a regression test (`apps/cli/tests/up-resume-derives-workflow.test.js`).

```sh
# Resume a detached run — no workflow path needed
bunx smthrs up --resume <runId>

# Retry one failed task inside a run; the invocation is detached,
# so closing this shell no longer kills the run
bunx smthrs retry-task <runId> <taskId>
```

**Operator impact.** For anyone driving runs from scripts or short-lived shells: the session that launched or retried a run is no longer a load-bearing part of the run's lifetime.

## Failover that actually fails over

**The failure mode.** You configure a fallback chain — Codex leads with alternates behind them — precisely so a single provider failure doesn't sink the run. Two bugs undermined that. Session-loss errors (including Kimi's "session is broken" banner) weren't classified as retriable, so the chain silently skipped Codex leads instead of retrying or falling through ([#1480](https://github.com/smithersai/smithers/issues/1480)). And a mixed agent-chain failure — different agents failing for different reasons — hard-failed the run outright ([#1482](https://github.com/smithersai/smithers/issues/1482)).

**What changed.** Session-loss errors are now classified, so the fallback chain retries the lead or falls through to the next agent. Mixed-chain failures park the run as **waiting-quota** instead of hard-failing it. The safe default is the important part: when every agent in the chain fails, the run waits in a resumable state rather than dying and discarding its position.

Both layers are covered: unit tests on the classifier (`packages/agents/tests/classifySessionLoss.test.js`, asserting the Kimi resume banner is recognized as session loss with the session id captured) and end-to-end suites (`packages/engine/tests/session-loss-chain-failover.e2e.test.jsx`, asserting a mid-chain failure advances the retry past it and records preflight skips on attempt metadata).

One more preflight fix in the same area: **Codex preflight no longer rejects valid ChatGPT auth when `auth.json` also contains an `OPENAI_API_KEY`** ([#1447](https://github.com/smithersai/smithers/issues/1447)). Keeping an API key alongside ChatGPT credentials no longer knocks Codex seats out of the chain before they run.

**Operator impact.** A provider outage, a broken session, or a quota wall now degrades to a parked, resumable run — not a dead one you discover in the morning.

## Gateway and UI discovery you can trust

**The failure mode.** The Gateway's `register()` rendered every workflow's `<UI>`/`<TUI>` declarations synchronously, pegging the event loop. In workspaces with many workflows, `/health` went unreachable for minutes — surfacing as `GATEWAY_UNREACHABLE` and `smithers ui` failures against a gateway that was, technically, running.

**What changed.** Discovery is now queued and batched: `register()` enqueues `<UI>`/`<TUI>` discovery instead of rendering inline, draining one render per macrotask, so `/health` stays live throughout. A 287-line regression suite (`packages/server/tests/gateway-view-discovery.test.jsx`) pins the behavior.

Two related discovery gaps closed alongside it:

- **Workflows launched by explicit path outside `.smithers` now register with the Gateway** ([#1474](https://github.com/smithersai/smithers/issues/1474)), so `smithers ui` finds their `<UI>` declaration.
- **Custom-path UIs (`<UI path="/custom">`) no longer 404 while discovery is still draining.** An unmatched UI request drains pending discovery once — each render still runs at most once — and re-resolves the mount.

**Operator impact.** Health checks answer during discovery, and the UI you declared is the UI you get, regardless of where the workflow file lives or how fresh the Gateway is.

## Correctness fixes for workflow authors

**Callable `ctx.outputs` resolves correctly** ([#1486](https://github.com/smithersai/smithers/issues/1486)). The callable form `ctx.outputs(outputs.probe)` indexed the snapshot with the raw argument and silently returned an empty array — a plausible-looking result that could send a downstream task confidently in the wrong direction. It now resolves through the same table-ref resolution as every other accessor, and an argument that resolves to no declared output table **throws**. Regression tests in `packages/driver/tests/ctx-outputs-table-ref.test.js` pin both behaviors:

```tsx
// Both forms now resolve to the same rows:
const byName = ctx.outputs("probe");
const byRef  = ctx.outputs(outputs.probe); // previously: silently []

// And an unresolvable argument throws instead of returning []
```

**Panel moderators no longer deadlock inside Ralph** ([#1487](https://github.com/smithersai/smithers/issues/1487)). Moderator `needs` omitted Ralph's iteration suffixes on dependency names, so a panel nested in a Ralph loop could wait forever on a node name that no longer existed.

**`smithers bug --run` attaches useful evidence** ([#1484](https://github.com/smithersai/smithers/issues/1484)). Bug reports filed with `--run` previously attached ~50 `TaskHeartbeat` events — roughly a 25-second window of noise — with an incorrect report title. Reports now attach lifecycle events with a correct title.

## New: the upgrade-dependents pack workflow

The one feature in this release is a new **`upgrade-dependents`** pack workflow. It discovers open-source dependents of the renamed npm package (via awesome-smithers, GitHub code search, and an `extraRepos` input), then runs one lane per dependent repo: a Luna agent clones, upgrades, and must prove `git grep` returns zero stale hits before a Sol reviewer independently re-checks the diff and a draft PR is opened — with a separate improvements PR or issue when a lane finds something beyond the rename.

It's Smithers dogfooding in the most literal sense: durable, review-gated, multi-lane workflows managing the project's own ecosystem migration across every downstream repo at once.

## Upgrading and what's next

There are **no breaking changes and no migration steps** in 0.33.1. Upgrading from 0.33.0 is drop-in:

```sh
bunx smthrs update
```

If you run long-lived or detached runs — anything that outlives the shell that started it — upgrade: this release removes several ways a run could die that had nothing to do with your workflow. After upgrading, a run that hits a provider outage parks as `waiting-quota` instead of failing, so check `bunx smthrs ps` before assuming anything died.

Get started or upgrade at [smithers.sh](https://smithers.sh).
