Everything a run has done is in its journal. A second process that wants to watch runs does not need authority over them; it needs the journal stream. `@smthrs/sync` is read-only journal replication: a server that pages and streams journal entries, and a client that follows one run or a whole workspace from durable cursors.

```ts
import { SyncProtocol } from "@smthrs/sync"
import * as Schema from "effect/Schema"

const scope = Schema.decodeUnknownSync(SyncProtocol.RunScope)({
  _tag: "Run",
  runId: "build-42"
})
const cursor = Schema.decodeUnknownSync(SyncProtocol.RunCursor)({
  runId: "build-42",
  afterSeq: 17
})
```

## The wire

The protocol is two RPCs. `Sync.Read` answers one bounded page of entries for a scope and a cursor set. `Sync.Subscribe` streams `Entries` frames, each carrying one run's entries and the interval the server covered, until the credit the request paid runs out or the server closes the stream. Credit is a hard limit on frames, not a sliding acknowledgement window: there is no Ack RPC, and a follower that wants more resubscribes from the cursors it has acknowledged. A cursor is per run and means "entries after this sequence"; journal sequences may have holes, so the next entry is not required to be exactly one greater.

A read stops at the first of three bounds: the request's `limit`, the frame ceiling, or the durable tail of every covered run, which is the only case that reports `done: true`. `RunCatalog` supplies the run list for a workspace read, and a workspace subscription reconciles the runs it covers against that list on every round, so a run created mid-follow joins the stream and a dropped notification costs latency, never state.

## What a follower can do

A follower projects the journal into whatever read model it needs: a dashboard, an audit trail, a search index, a materialized view of run state. It inspects any run its credential covers, catching up through `Sync.Read` until the server reports done and then following live through `Sync.Subscribe`. `SubscribeOptions.apply` upgrades a cursor from delivered to applied: the callback runs to success before the cursor moves, so a consumer whose own write fails re-receives the entry instead of skipping it. A lost transport reconnects under exponential backoff capped at five seconds, resuming from the acknowledged cursors. When compaction deletes entries below a cursor, the client moves that run's cursor to the checkpoint and restarts the subscription, and `SubscribeOptions.onResync` runs before the move and must succeed, so nothing is skipped silently.

## What a follower never does

A follower never writes. The wire carries no submission path: client-to-server commands are `BranchRpcs`, which has no production mount at 1.0.0-rc.0, so the gateway serves `SyncRpcs` alone. A follower never claims a run and never resumes one. Ownership stays with engines, and a follower holds no lease, no fence, and no dispatcher. Sync is not a control channel: steering and approvals belong to the control plane, not the journal feed.

## Principals and authorization

Every request is answered against a principal, and the default is anonymous. Over RPC, `SyncAuth.layer` establishes the workspace principal by verifying the `WorkspaceShare` capability in the `flows-sync-workspace` header; a header that is malformed, forged, expired, or signed by an unknown key is refused outright rather than downgraded to anonymity. A run mapped to a shared branch is visible only under a `BranchShare` capability, and without one every branch run is closed. Both capabilities are HMAC-SHA-256 signatures over a length-prefixed encoding of their claims, led by a scheme label so one cannot be replayed as the other. Secrets are `Redacted`, and a `kid` lets keys rotate without invalidating capabilities minted under a retired one. A subscription is authorized once, when it opens, and ends with `unauthorized` when the signed expiry arrives, because a stream that stayed connected would otherwise outlive its credential.

## Why followership fits dashboards and auditors

A dashboard or an auditor needs the whole truth and zero authority. Followership is exactly that shape: the follower sees everything its principal covers and can affect nothing. A follower that is slow, wrong, or compromised cannot mutate a run, hold a lease, or block a producer; its worst outcome is stale output. Every fan-out surface is bounded, so one follower's cost is a function of the configured bound rather than of the workspace's size or of how far behind it has fallen. Change feeds slide rather than block, so a stalled subscriber costs itself latency and never grows the publisher.

## Trade-offs

Server responses are admitted, never trusted. A frame that carries another run's entry, repeats or reorders a sequence, or serves an entry at or below the cursor is refused as a `protocol_violation` before any cursor moves.

- The frame ceiling (default 1 MiB) is a budget on one page, not a verdict on the read: a page that would cross it reports `done: false`, and only a single entry larger than the ceiling fails `frame_too_large`.
- One page is shared across the runs it covers, so a run with a backlog takes the larger part but never all of it, and a bootstrapping follower reaches the runs behind a busy one.
- The `Heartbeat` frame is reserved and no server emits one at 1.0.0-rc.0: keepalive is a transport concern, because a heartbeat here would spend the subscription's credit.
- A resync moves a cursor, not state. The wire carries no checkpoint state, so a follower with derived state restores the compacted prefix out of band before the cursor moves.
