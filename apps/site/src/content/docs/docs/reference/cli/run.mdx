## Synopsis

```text
smthrs run <plan-payload>
smthrs run <run-id> --resume
```

## Description

`smthrs run` launches the flow an approved plan payload authorizes, or with `--resume` re-drives a parked run. The payload is the complete authority: `run` never plans and never approves, so a payload whose plan has no approval yet parks the run at `waiting-approval` and exits 3. When this process owns the executor, an attached launch stays until the run settles and the command exits with the run's terminal status. `smthrs resume <run-id>` is an unlisted alias of `run --resume`: both spellings share one implementation and one idempotency key, and neither appears in `--help`.

A run that asks for approval mid-flight journals a `control.approval.requested` event whose `payload` field is the exact argument for `smthrs approve`; after the decision, `run --resume <run-id>` re-drives the parked execution.

## Arguments

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `plan-payload` | JSON string | yes, without `--resume` | The complete serialized approval payload from `smthrs plan`. |
| `run-id` | string | yes, with `--resume` | The durable run to re-drive, occupying the same positional argument. |

## Flags

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--resume` | boolean | `false` | Treat the argument as a run id and resume the parked run instead of launching a payload. |
| `--remote <url>` | URL | none | Act on a remote control plane. A remote invocation owns no executor, so there is no settlement wait: the printed receipt is the whole answer. |

## Output

Prints the control plane's receipt for the launch or resume:

| Receipt | Meaning |
| --- | --- |
| `Accepted` | The run launched; `runId` names it. |
| `Parked` | The plan lacks approval; the run waits at `waiting-approval`. |
| `Terminal` | The run already settled; `status` says how. |
| `AlreadyApplied` | The same idempotency key already launched this run. |
| `Conflict` | The idempotency key was used for a different mutation. |

The human rendering indents the receipt; `--json` prints it compact. A script reads `runId` from the `Accepted` document whatever the run does next:

```json
{"_tag":"Accepted","receiptId":"<receipt-id>","runId":"<run-id>"}
```

If the executor declines the launch (no seat resolved, a capability not granted, or the flow belongs to another host), `run` prints the run's summary instead and exits 1; `smthrs status <run-id>` shows what such a run waits for.

## Exit codes

| Code | When |
| --- | --- |
| `0` | The launch was accepted, or the run settled `completed`. |
| `1` | The run settled `failed`, the executor declined the launch, or a live peer owns the run (`ClaimLost: claim_lost runId=<run-id>`). |
| `2` | The payload was not valid JSON, did not match the approval schema, or targeted an in-run ask (`run requires a plan approval payload`). |
| `3` | The plan has no approval yet; the run parked at `waiting-approval`. Answer with `smthrs approve`, then resume. |
| `130` | The run settled `cancelled`. |
