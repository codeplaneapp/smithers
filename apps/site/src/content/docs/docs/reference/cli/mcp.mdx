## Synopsis

```text
smthrs mcp add [--agent <claude|codex>]
```

## Description

`mcp add` registers the Smithers stdio MCP server in an agent's own configuration, so the agent can plan, run, and inspect flows through the MCP tool surface. This release knows two agents: `claude`, configured at `~/.claude.json`, and `codex`, configured at `~/.codex/mcp.json`. Writing is additive and idempotent: your other servers stay in place, an entry that is already correct is left alone, and a file that cannot be parsed is reported rather than replaced. It never removes entries and never edits any other part of the configuration.

The registered launch command is the running CLI itself with `--mcp`, so an installed CLI registers its own installed path.

## Flags

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--agent <id>` | string | none | Which agent to wire: `claude` or `codex`. Omitted wires every known agent. Any other id exits 2 and names the known ones. |

## Output

Prints one entry per target agent with `agent`, the configuration `path` it wrote or kept, the `status` (`written`, `unchanged`, or `failed`), and a `reason` when the write failed. When every target fails, the manual registration instructions print to stderr instead and the command exits 1. `--json` prints the same entries in compact JSON.

## Serve MCP over stdio

`--mcp` is a flag on the `smthrs` binary, not a verb, because an MCP client's configuration names a launch command: `mcp add` writes that command into the agent's config, and the client starts the server itself.

```text
smthrs --mcp [--surface semantic|raw|both] [--allowed-tools <a,b>] [--read-only]
```

In this mode the binary speaks newline-delimited JSON-RPC 2.0 over stdio (MCP protocol revision 2025-06-18) until standard input closes. Every tool result is the `{ ok, data?, error? }` envelope, serialized into the text content block and repeated as structured content. Frames larger than 4 MiB are refused.

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--surface <name>` | string | `semantic` | Which tool families the session exposes: `semantic` (the named control tools), `raw` (one directory tool per shipped CLI verb, pointing at the command and its semantic equivalent), or `both`. Any other spelling falls back to `semantic`. |
| `--allowed-tools <a,b>` | string | none | Comma-separated tool names; the session exposes only these. Omitted exposes the whole surface. |
| `--read-only` | boolean | `false` | Expose only read-only tools. |

Both `--flag value` and `--flag=value` spellings work. Ten 0.x tool names remain on the semantic surface and answer `{ ok: false, error: { code: "unsupported" } }` with the reason, so an agent is told that time travel, checkpoints, and human questions are features this release does not have.
