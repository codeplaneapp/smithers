Smithers running inside a real stereOS VM

A stereOS mixtape boots under a hypervisor, and a Smithers <Sandbox> runs its body inside that VM over the shipped provider kit.

This one really boots stereOS. The recording below is captured output from apps/stereos-site/real/, not a simulation. mb up boots the published coder mixtape (stereOS 2026.03.04.0, Linux 6.12.74 aarch64) on Apple's hypervisor in about seven seconds. smithers up stereos-real.tsx then drives a <Sandbox> whose provider is 80 lines of SSH on top of createCommandSandboxProvider from smthrs/sandbox. Every value in the run output was measured inside the guest by the agent user.

The proof that the work happened in the VM, and not on the host that started it: the guest hashes the prompt the host sent it, and reports its own kernel, user, and restriction state. Nothing in that output is available to the host except through the VM.

The entry-runner gap

Mixtapes ship agent harnesses, not Bun or Node, so the usual bun run-smithers-sandbox.js entry does not exist in the guest. This run uses the dependency-free alternative: a POSIX shell runner uploaded with the request, which reads SMITHERS_SANDBOX_REQUEST_PATH and writes SMITHERS_SANDBOX_RESULT_PATH — the same contract every first-class provider uses. A smithers-mixtape carrying Bun and the standard runner would remove this file entirely.

What the guest reported

Read the tail of the recording. writeOutsideWorkspace: denied is the restriction model holding: the agent user cannot write to /etc. nixCli: on PATH is a gap — the restricted PATH comes from the agent's login shell, so a non-interactive SSH exec still sees the full system profile.

Smithers running in your browser

A WebContainer boots Node, installs the published smthrs package, and runs real workflows against the PGlite backend.

This tab simulates the seam; the “Real stereOS” tab boots the VM. The engine below is the published smthrs package on npm, running under Node inside a WebContainer in this tab. The workflows, the PGlite database, the gateway, and the approval decision are all real. The sandbox provider uses the same provider kit and the same request/result contract as the stereOS provider, but its SSH → microVM transport is swapped for in-container exec, because a browser cannot boot QEMU. Nothing in this tab runs stereOS.

No API keys and no agent seats are involved. The three workflows use literal-value tasks and a human approval gate, so every step is deterministic.

How the approval works

smithers up exits when it reaches the gate, leaving the run in waiting-approval. Clicking Approve in the panel on the right posts the decision through the gateway. The page then resumes the run with smithers up workflows/approval-demo.tsx --resume --run-id <id>, and the second task runs.

Running smthrs under Node

The published package targets Bun. Six things make it run under Node, all applied to the project mounted in the container:

  • overrides.effect pinned to a single version. Without it npm installs about twenty copies of effect and the engine fails its Context lookup.
  • Loader shims that map bun, bun:sqlite, bun:test, and drizzle-orm/bun-sqlite to stubs. Node rejects the bun: URL scheme before any runtime guard can run.
  • SMITHERS_BACKEND=pglite, so the store never reaches for bun:sqlite.
  • A one-line postinstall patch to openSmithersBackend.js, so the cross-run memory sidecar is skipped when Bun is undefined.
  • An in-process PGlite client. The PGlite socket server accepts a WebContainer connection but does not complete its PostgreSQL handshake.
  • A single-writer transaction path. Effect 4 does not unwind a nested transaction operation after successful PGlite writes in WebContainer. The demo keeps every write and omits only multi-writer grouping. It runs one writer at a time.

The demo project is committed at apps/stereos-site/project. Tab 1 is the design reference and describes an integration that does not exist yet.
