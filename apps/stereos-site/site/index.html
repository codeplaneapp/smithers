    1. Integration model

    Both systems already meet at a clean seam:

    LayerSmithers ownsstereOS owns
    OrchestrationWorkflow graph, retries, approvals, replay, diff review, outputs—
    Task boundary<Sandbox>: one scheduler task that runs a child workflow elsewhere—
    TransportProvider kit: request/result JSON files + an exec channelSSH (dev variant) today; agentd/vsock later
    Execution host—Hardened NixOS microVM (a booted mixtape)
    Inner isolation—gVisor sandbox per agent, read-only /nix/store rootfs, restricted agent user
    Environment identityimage / workspace.snapshotId propsNix flake: bit-for-bit reproducible images

    The integration is one adapter: a SandboxProvider whose session boots (or reuses) a stereOS VM, copies the Smithers request bundle in, runs the entry command as the agent user, and reads the result bundle back. Smithers treats it exactly like its Microsandbox, Daytona, Vercel, AWS, GCP, and Cloudflare providers.

    3. Provider contract and provider kit shipped

    A provider is two functions. First-class providers implement neither directly: they call createCommandSandboxProvider from smthrs/sandbox, which owns the request/result protocol, and supply only a SandboxSession:

    type SandboxProvider = {
  id: string;
  run(request: SandboxProviderRequest): Promise<SandboxProviderResult>;
  cleanup?(request: SandboxProviderRequest): Promise<void>;
};

// The seam a provider author actually implements:
type SandboxSession = {
  readonly remoteId: string;
  readonly writeFile: (path: string, content: string) => Promise<void>;
  readonly readFile: (path: string) => Promise<string>;
  readonly exec: (command: string, opts: { cwd: string; env: Record<string,string>;
                   timeoutMs: number; signal?: AbortSignal }) => Promise<{ exitCode: number;
                   stdout: string; stderr: string }>;
  readonly destroy?: () => Promise<void>;
};

    The kit writes the request JSON into the sandbox, sets SMITHERS_SANDBOX_REQUEST_PATH and SMITHERS_SANDBOX_RESULT_PATH, runs the entry command, and parses the result from stdout or the result file. The entry command returns either { bundlePath } or a structured { status, output, remoteRunId?, workspaceId?, diffBundle? }. Bundle limits: 100 MB total, 1,000 patch files, no symlinks or path traversal. Secrets never enter the request JSON; redactSandboxProviderValue() scrubs anything named like a credential from errors, heartbeats, and audit rows.

    4. What stereOS provides

    stereOS (papercomputeco/stereOS, Paper Compute) is a NixOS-based Linux OS purpose-built for running coding agents:

    • Mixtapes. Flake-built machine images bundling the hardened OS with an agent harness: opencode-mixtape, claude-code-mixtape, gemini-cli-mixtape, full-mixtape. Each ships a production variant (no SSH) and a -dev variant (SSH key injected from ~/.config/stereos/ssh-key.pub).
    • Three boot formats. Raw EFI image (stereos.img, Apple Virtualization Framework), QCOW2 (QEMU/KVM), and direct-kernel artifacts (bzImage/initrd/cmdline) for 2–3 second boots. Plus an AWS Lambda MicroVM target.
    • Security model. Restricted agent user confined to /home/agent/workspace, denied the Nix daemon and package tools; admin user for operations; gVisor sandboxes with a read-only /nix/store rootfs for the inner layer; kernel hardening; ephemeral temp storage.
    • Daemons. stereosd (system control plane) and agentd (agent lifecycle). Public exec/file APIs for these are not yet documented; see §8.
    • Reproducibility. The whole system is a Nix flake (nixosConfigurations.base|coder + -dev variants, nixosModules.default); an image hash fully determines the environment.

    5. createStereosSandboxProvider(options) proposed

    Proposed package smthrs/stereos, provider id stereos. Option surface mirrors the shipped Microsandbox provider so nothing here is novel to Smithers users. Every option maps to a real stereOS or hypervisor feature.

    6. Prop mapping: Smithers control → stereOS behavior

    Smithers controlstereOS / hypervisor behavior
    imagePath to a mixtape artifact; overrides mixtape/format selection.
    envPer-command env over the exec channel; the guest also enforces its own restrictions (the agent user cannot touch the Nix daemon regardless of env).
    allowNetwork={false}User-mode netdev with restrict=on: the hostfwd SSH channel still works, but no guest-initiated outbound flows. (True network-off needs the vsock transport, §8.)
    allowNetworkStandard user-mode NAT; the guest's own hardening still applies.
    portsExtra hostfwd mappings on the netdev.
    volumesvirtio-9p/virtiofs shares mounted into the guest; read-only by default. Never mount credentials or the host Nix store writable.
    cpuLimit / memoryLimit-smp / -m, rounded up (whole vCPUs, MiB).
    workspace.persistence: "sticky"Named copy-on-write QCOW2 overlay kept across runs; the base mixtape image is never written.
    workspace.persistence: "ephemeral"Overlay deleted at cleanup (or QEMU -snapshot: nothing ever hits disk).
    workspace.snapshotIdBoot from a saved overlay. Disk state only. There is no memory or process preservation (the same caveat as Microsandbox snapshots).
    commandExecuted via the exec channel as the agent user in workdir.
    egress.*Proxy env projected into the command env; caCertPem uploaded into the guest and pointed at by NODE_EXTRA_CA_CERTS.
    reviewDiffsEntry runner emits a diffBundle from the workspace (git/jj diff); Smithers gates application on review as usual.

    7. Getting it up and running

    7.1 Prerequisites

    • Nix with flakes enabled (the Determinate installer is the fast path).
    • QEMU: brew install qemu (macOS) or apt install qemu-system-x86 (Linux).
    • Hardware virtualization: KVM on Linux, HVF/Apple Silicon on macOS.
    • macOS caveat: mixtapes are Linux systems (x86_64-linux/aarch64-linux), so building them on a Mac needs a Linux builder (nix run nixpkgs#darwin.linux-builder, or Determinate Nix's built-in one). Expect this to be the roughest edge; building on any Linux box and copying the artifact over also works.

    7.2 Build and boot a mixtape (standalone, no Smithers yet)

    # One-time: the key the -dev mixtape bakes in for SSH
mkdir -p ~/.config/stereos
ssh-keygen -t ed25519 -f ~/.config/stereos/ssh-key -N ""

git clone https://github.com/papercomputeco/stereOS
cd stereOS

# Build a dev-variant image (SSH enabled). claude-code-mixtape bundles Claude Code.
make build-qcow2 MIXTAPE=claude-code-mixtape-dev ARCH=x86_64-linux
# or, for 2-3s direct-kernel boots on Linux/KVM:
make build-kernel MIXTAPE=claude-code-mixtape-dev ARCH=x86_64-linux

# Boot it
make run SSH_PORT=2222

# Verify both users
make ssh-agent    # lands in /home/agent/workspace (restricted user)
make ssh-admin    # operations user

    Inside the guest, the harness is on PATH and keyed by env (export ANTHROPIC_API_KEY=... && claude in the claude-code mixtape). Confirm the restriction model: as agent, nix and package tools are denied and writes outside ~/workspace fail.

    7.3 Wire it into Smithers today (no new package needed)

    This inline provider is complete and uses only shipped Smithers APIs (createCommandSandboxProvider + an SSH-backed session). It assumes the VM from §7.2 is booted. This is the ~80-line PR seed for smthrs/stereos.

    /** @jsxImportSource smthrs */
import { createSmithers, Sandbox } from "smthrs";
import { createCommandSandboxProvider } from "smthrs/sandbox";
import type { SandboxSession } from "smthrs/sandbox";
import { z } from "zod";

const SSH_ARGS = [
  "-p", "2222", "-i", `${process.env.HOME}/.config/stereos/ssh-key`,
  "-o", "StrictHostKeyChecking=accept-new", "agent@127.0.0.1",
];
const q = (s: string) => `'${s.replace(/'/g, `'\\''`)}'`;

async function ssh(cmd: string, stdin?: string) {
  const proc = Bun.spawn(["ssh", ...SSH_ARGS, cmd],
    { stdin: stdin === undefined ? "ignore" : new Response(stdin).body ?? "ignore" });
  const [stdout, stderr, exitCode] = await Promise.all(
    [new Response(proc.stdout).text(), new Response(proc.stderr).text(), proc.exited]);
  return { exitCode, stdout, stderr };
}

export const stereosProvider = createCommandSandboxProvider({
  id: "stereos",
  workdir: "/home/agent/workspace",
  command: "bun /home/agent/workspace/run-smithers-sandbox.js",
  cleanup: "keep", // VM lifecycle is manual in the inline version
  async createSession(request): Promise<SandboxSession> {
    return {
      remoteId: `stereos-${request.sandboxId}`,
      async writeFile(path, content) {
        await ssh(`mkdir -p $(dirname ${q(path)}) && cat > ${q(path)}`, content);
      },
      async readFile(path) {
        const r = await ssh(`cat ${q(path)}`);
        if (r.exitCode !== 0) throw new Error(r.stderr);
        return r.stdout;
      },
      async exec(command, opts) {
        const env = Object.entries(opts.env)
          .map(([k, v]) => `${k}=${q(v)}`).join(" ");
        return ssh(`cd ${q(opts.cwd)} && env ${env} ` +
          `timeout ${Math.ceil(opts.timeoutMs / 1000)} ${command}`);
      },
      // destroy omitted: a real provider powers off QEMU and reaps overlays here
    };
  },
});

    Then use it like any provider:

    import childWorkflow from "./child-workflow";

const { Workflow, smithers, outputs } = createSmithers({
  input: z.object({ prompt: z.string() }),
  result: z.object({ summary: z.string() }),
});

export default smithers((ctx) => (
  <Workflow name="stereos-run">
    <Sandbox
      id="isolated-edit"
      provider={stereosProvider}
      workflow={childWorkflow}
      input={{ prompt: ctx.input.prompt }}
      output={outputs.result}
      allowNetwork
      reviewDiffs
    />
  </Workflow>
));

    The entry runner (run-smithers-sandbox.js, delivered via setupFiles or baked into a future smithers mixtape) reads SMITHERS_SANDBOX_REQUEST_PATH, executes the child workflow, and writes the result JSON to SMITHERS_SANDBOX_RESULT_PATH. This is the command-provider request/result contract. Note the mixtapes ship agent harnesses, not Bun; until a smithers mixtape exists, upload a self-contained runner or use the harness itself as the entry.

    7.4 What the first-class package adds over the inline version

    • VM lifecycle owned by the provider: build/boot per vmName, overlay management, sticky workspaces, cleanup: "destroy", idle/max-duration caps.
    • Prop mapping from §6 (ports, volumes, limits, snapshots) instead of a fixed QEMU invocation.
    • Heartbeats during boot, abort-signal kill of guest processes, contract-suite tests via createSandboxProviderContractSuite.

    8. Integration gaps

    Each gap is a concrete question for Paper Compute, and each is answerable with a small, well-scoped contribution:

    #GapQuestion / contribution
    1Production mixtapes have no SSH, and agentd/stereosd expose no documented exec or file API.Is agentd getting a host-facing exec/file API (vsock or HTTP)? That API is exactly Smithers' SandboxSession seam. SSH then becomes a dev-only fallback and variant: "prod" becomes usable.
    2The entry command currently runs as the agent user directly; stereOS's inner gVisor sandboxes are launched by its own tooling.How should third-party orchestrators target the gVisor layer? Is "spawn me a sandbox running this command" an agentd verb?
    3No mixtape carries a Smithers runner (or Bun).A smithers-mixtape in mixtapes/: Bun + the sandbox runner baked in. PR-sized; makes stereOS a boot-and-go Smithers execution host and gives Paper Compute an orchestrator integration to point at.
    4Telemetry stays inside the guest.The tapes seam: Smithers persists every run event and supports replay/fork/time-travel; a tapes exporter for Smithers runs gives their console an orchestrator data source. Symmetric to #3.
    5Self-hosting story.For a customer who requires on-prem agent execution (the Optimism-style requirement), "boot this mixtape" replaces "run our install scripts on your Ubuntu box": reproducible, auditable, hardened by default.
