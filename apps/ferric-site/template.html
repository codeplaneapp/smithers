React's runtime, rewritten in Rust.

Ferric is an unofficial Rust/WASM implementation of React's engine — the reconciler, the scheduler, the DOM commit path, streaming SSR, and the Server Components protocol. It is judged by exactly one thing: React's own unmodified test suite. And the entire port is executed by a single durable workflow you can read from top to bottom.

“One durable workflow ported React's complete OSS web runtime to Rust/WASM, passed the unchanged upstream test suite, and published reproducible benchmarks.”

That sentence is the whole project. Everything below exists to make it either true or provably false — never “sort of true.” React is a trademark of Meta; Ferric ships under its own names (@ferric/*, ferric-react*) and never under upstream ones.

01The claim, and how you would falsify it

Most “rewrote X in Rust” projects grade their own homework: they port a subset, write fresh tests for the part that works, and publish a benchmark. Ferric's rule is the opposite — the command is the claim:

···@@ the definition of "passes React's test suite" @@
1 yarn test --build -r=stable # DEV + --prod
2 yarn test --build -r=experimental # DEV + --prod

Green on all four, at a pinned React commit, with jest configs checksummed and zero tests skipped, deleted, or edited. That alone is not enough, because a port could quietly fall back to the JavaScript it is replacing and still pass. So four more rules hold the claim honest:

  • A backend assertion. With REACT_RUST_ASSERT_BACKEND=1, any root or request that touches a JavaScript fallback fails the test. An import audit proves no ported JS implementation path even loads.
  • A signed baseline. Test identities, file hashes, config hashes, and flag values are recorded up front and diffed before every landing — so the denominator can never quietly shrink.
  • A public xfail ledger in three buckets: source-mode-only, compiled-out dead flags, and genuine regressions. The third bucket must be zero at ship.
  • Differential fuzzing. 100M+ generated trees and interaction scripts run against both engines; identical DOM, identical scheduler yield logs, identical console output, or it is a bug.

Why this bar, specifically?

React's test suite is unusually good at catching semantic drift: it asserts on warning text, effect ordering, scheduler yields, and hydration mismatches — the exact things a reimplementation gets subtly wrong. Borrowing it wholesale means the project cannot define its own success. If Ferric is wrong, someone else's tests say so.

02How React is actually architected

To follow the port you need React's internals at a level most React developers never need. Here is the whole engine in one pass.

Elements, fibers, and two trees

JSX compiles to plain objects — { type, props, key }. These elements are immutable descriptions, not the engine's working state. For each element React keeps a fiber: a mutable node holding the component type, its state, its hooks, its effect flags, and links to its child, sibling, and parent. Fibers form the tree the engine actually walks.

There are always (at most) two trees: the current tree on screen, and the work-in-progress tree being built. Each fiber points at its counterpart through alternate, and React double-buffers between them. That is why a render can be thrown away safely — the current tree was never touched.

The two phases

Phase 1 · interruptible
Render
beginWork descends the tree calling your components; completeWork ascends building host instances. Can be paused, resumed, or thrown away — so it must be pure.
Phase 2 · synchronous
Commit
Applies the result to the host in sub-phases: before-mutation snapshots, mutation writes the DOM and detaches refs, layout attaches refs and runs useLayoutEffect. Then passive effects (useEffect) flush asynchronously.

The commit is not a simple loop — it is an interruptible state machine that can park mid-flight (waiting on stylesheets, view transitions, gestures), with root.current flipping between the mutation and layout phases. Getting that ordering wrong is invisible until an effect fires against the wrong tree.

Lanes and the scheduler

Priority is a bitmask called lanes: a click is a different lane from a transition, which is different from an idle update. The scheduler is a separate package that hands the reconciler slices of time and asks it to yield roughly every 5ms so the browser can paint. Tests substitute their own mock scheduler to control time — which turns out to matter enormously for the port.

Hooks

useState and friends are a linked list hanging off the fiber, resolved by call order. React swaps a “dispatcher” depending on whether it is mounting or updating, which is how the same useState call does two different things. There is no name-based lookup — position is identity.

The host config: the seam that makes this possible

The reconciler does not know what a DOM is. It talks to a host config: roughly forty functions like createInstance, appendChild, commitUpdate. react-dom is one implementation; React Native is another; the test and noop renderers are two more that exist purely for React's own test suite.

This is the hinge of the entire project. Because the reconciler is already host-agnostic, Ferric can port the reconciler first and validate it against the noop renderer — 76 test files and 1,039 cases of pure semantics — long before touching a single line of DOM code.

Fizz and Flight

Two more state machines ship in the same repo. Fizz is streaming server rendering: it walks the tree emitting HTML chunks, splitting at Suspense boundaries, handling abort and backpressure, and the exact byte order of those chunks is observable. Flight is the React Server Components protocol: it serializes a component tree to a wire format the client deserializes. Both are in scope.

03Where the Rust/JavaScript line goes

You cannot move all of React into Rust, and pretending otherwise is how these projects die. JavaScript object identity is observable (Object.is drives every bailout), your components are JavaScript closures, and the DOM lives in JavaScript. So Ferric draws one line, and four independent planners converged on the same place:

Rust owns
Structure & decisions
The fiber tree, lanes, scheduler internals, diffing, commit planning, hooks bookkeeping, and the Fizz/Flight state machines.
JavaScript owns
Identity, values, the DOM
Elements, props and state values, user closures, actual DOM mutation, and synthetic events.
Rust/WASMJavaScript

The rule of thumb: one boundary crossing per component render, per hook dispatch, per effect — and everything else engineered away. Child sets are consumed in bulk rather than one call at a time. DOM work is batched into phase-scoped command buffers instead of chattering. Values that stay JavaScript are referenced by generational handles ({slot, generation}) so a stale reference is caught, not silently wrong. Identity comparisons are batched.

The risk that decides the project

Every crossing costs something. A realistic update touches thousands of fibers, so if the boundary tax is too high, a Rust engine can be slower than the JavaScript one it replaces — and the whole exercise is pointless. That is why the first real gate is an economic one: a throwaway spike must land within 1.5× of upstream on a partial-update benchmark after at most two protocol revisions, or the project pivots to server-rendering only, or stops.

Scope, stated plainly

In scopeOut of scope, and why
scheduler, shared, react-is, react, react-reconciler, react-dom-bindings, react-dom, react-server (Fizz + Flight), react-client, react-server-dom-webpack, react-markup, plus the test and noop renderers as oracle hosts. DevTools apps, React Native, react-art, the compiler, the ESLint plugin, non-webpack Flight adapters, and Meta-internal channels. These are separate products or separate hosts; porting them would not exercise the browser runtime.

Two deliberate exceptions: the react package itself and the synthetic event system stay JavaScript by published design decision — they are about identity and DOM, not engine structure. They are still fully judged by the suite.

05Wait — what is Smithers?

If you arrived for the Rust part: Smithers is a durable control plane for long-running AI agents. A workflow is a TypeScript file that looks like React (it is a React reconciler, with tasks instead of DOM nodes), and the runtime renders it in a loop: figure out what can run now, run it, persist the result, render again.

The properties that matter for a 16-week port:

  • Every finished step is persisted. Crash the machine and the run resumes from the last completed task — it never redoes finished work.
  • Humans are nodes in the graph. An approval gate is a durable pause, not a process sitting in memory. A run can wait three days for a decision at zero cost.
  • Isolation is built in. Each agent works in its own git/jj worktree, so parallel lanes cannot corrupt each other's files.
  • Everything is inspectable and replayable. Each frame is a snapshot; you can rewind, fork, and re-run any node.

The campaign is deliberately one workflow — a single launchable graph, frozen and hashed before launch, with no sub-workflow and no second entry point. Not a pile of scripts a human babysits.

One workflow does not mean one file. The graph itself is small enough to read in a sitting; the pieces it composes live where Smithers expects them:

WhereWhatWhy there
workflows/react-rust-port.tsxThe graph: which milestone runs, the budget envelope, the error boundary, the hand-off.The shape of the campaign, readable end to end without wading through prompt text.
components/ferric/*.tsxThe machine: the slice loop, the verifier, the landing queue, each milestone phase.One export per file, so a piece can be read, tested, and reasoned about on its own.
prompts/ferric-*.mdxEverything said to an agent, as MDX components with typed props.Prompts are the highest-leverage text in the system. Editing one shouldn't mean editing the graph, and the output schema is injected automatically so the prompt and its validator cannot drift apart.

06The conversion, step by step

This is the actual machine. Each step below explains what happens, why it exists, and how it is enforced — and every one can be expanded to the real code that runs it, extracted from the workflow at build time.

00

Before anything: prove the launch is sane

WhatA single compute task runs before any model is paid: the launch directory must be the campaign repository, the deterministic script layer must exist, and the workflow greps its own source for illegal patterns.
WhyThree separate blind implementations of this workflow died on the same two bugs — worktrees forked one repository while landings merged into another, and the “deterministic” layer called scripts that nothing ever created. Both are cheap to detect and fatal to discover late.
HowPath identity is checked through symlinks; missing scripts fail closed after M0; and a self-audit asserts exactly one approval site and zero auto-approvals exist in the file. Any failure throws before the first token is spent.
Show the foundation gate
01

M0: build the oracle before building anything else

WhatThe first milestone writes no Rust at all. It builds the test harness that will judge every later line: React's build-mode configuration wired to run the four cells, the backend assertion, and a signed baseline manifest of every test identity.
WhyA port that builds its judge after its code will build a judge that agrees with its code. Freezing the oracle and the benchmark contract first is what makes the final claim falsifiable rather than self-congratulatory.
HowAn implementer authors the harness, then a compute task runs it against unmodified React and requires a full pass — the runner must prove itself on code known to be correct before it is trusted to judge new code.
Show the M0 oracle verification

Known defect, found by the blind review round and not yet fixed: this task trusts the PASSING=n/m line printed by a script an agent wrote, so a stub that prints PASSING=1/1 would satisfy it. The fix is for the verifier to invoke React's normative commands itself and check the count against the signed manifest. See Status — we publish the open holes rather than hide them.

02

Turn 81 modules into a landing order — and refuse a bad one

WhatThe reconciler's modules are parsed into work items: 22 leaf modules that can land independently, and one strongly-connected import cycle of 59 modules that cannot be split, grouped instead into six feature cohorts.
WhyMeasured with a cycle-detection pass, 59 of the reconciler's modules import each other circularly — there is no per-module landing order for the core. Handing those 59 files to parallel agents guarantees merge hell: every lane rewrites the same files from the same base.
HowThe parse is a machine check, not advice, and it checks semantics rather than counts: every cycle module assigned exactly once, every cohort inside hard size and line bounds, and every cohort gated on test files that actually exist in the pinned checkout. An earlier version counted to 59 and passed a 29-module cohort stamped with a blanket suite. Cohorts then land strictly one at a time, and only after every leaf has landed — enforced by the shape of the graph, not by asking an agent nicely.
Show the queue contract and the lane policy
03

One slice: implement in an isolated lane

WhatA slice is one vertical unit of work — a module or cohort, ported with its tests green. An implementer agent works inside a dedicated worktree on its own branch.
WhyVertical slices are the only unit that can be judged. “Ported 60% of the reconciler” means nothing; “this cohort's 1,039 cases pass through the noop host” is a fact. Isolation means four lanes can run at once without corrupting each other's checkouts.
HowThe prompt carries the porting rules (Rust owns structure, nothing recurses on tree depth, no stubs, warnings byte-identical) plus every blocking finding from the previous round, so each attempt starts from the last one's failures rather than from scratch.
Show the slice loop and its convergence rule
04

Two adversarial reviewers, from different model families

WhatEvery slice is reviewed by two independent agents that see only the diff, are told to assume it is wrong, and must produce findings — never a thumbs-up.
WhyA model reviewing its own work agrees with itself. Two reviewers from different families disagree in different directions, which is the point. Only critical and major findings block, so review cannot become a nitpick denial-of-service.
HowThe reviewers are structurally disjoint from the implementer — when a slice escalates to a stronger model, the reviewer on that family swaps to the other tier, so the model that wrote a slice can never review it.
05

The deterministic verifier — the one voice with a veto

WhatA compute task with no model attached runs real commands inside the lane: diff against the fork point, compile, scan for stubs, run the slice's mapped test cohort.
WhyReviewers are opinions; this is evidence. In the blind bake-off that produced this design, three of five implementations had a verifier that could return green without testing anything real — one ran the tests against the wrong branch, one read the implementer's self-reported booleans, one passed when a regex missed. Each quietly voided the project's central claim.
HowIt executes in the lane's own worktree, refuses “zero tests ran” as a pass, and distinguishes infrastructure death (out-of-memory, timeout — retry with headroom) from a real red. Its verdict gates both the fix loop and the right to land, so no reviewer and no human approval can override it.
Show the verifier and the infra-vs-red rule
06

Landing: one queue, and a ratchet that can only go up

WhatApproved slices merge one at a time through a single-lane queue. After each merge the full oracle re-runs; if the passing count went down, the merge is reverted and landing halts until a human clears it.
WhyParallel merges into one base branch is how a port silently loses work. And a suite that goes green-red-green over weeks is not evidence of progress — the monotone ratchet is what turns “tests pass” into “tests have never stopped passing.”
HowEvery landing task mounts inside the same named merge queue, which the engine pools into one lane across every worktree. The ratchet ledger has exactly one writer, and the measurement happens after the merge, on the merged tree — not on the lane that hoped it would work.
Show the landing task and the ratchet
07

Gates: the places a human can stop it

WhatEvery human decision in the campaign is a row in one registry, rendered through a single approval component. Kill gates, budget gates, the release candidate, every publication, and the M9 API freeze.
WhyA gate that can auto-approve under schedule pressure is not a gate. Concentrating them in one place makes “no gate auto-approves” a property you can check rather than a promise.
HowThe workflow audits its own source at runtime: if a second approval site or any auto-approval option ever appears in the file, the foundation task fails the run. Humans may deny, tighten, or de-scope — but no human decision can turn a deterministic red into a green.
Show the gate registry and the single approval site
08

Publishing: decide, gate, then act exactly once

WhatReleases are split into three nodes: an agent decides and justifies, a human approves, and a deterministic task performs the publish — last in the entire graph.
WhyPublishing is the one irreversible act here. An agent that decides to publish and publishes in the same step cannot have that decision reviewed or replayed without risking a second release.
HowThe act is keyed by an idempotency marker derived from the artifact and version, so a retry is a no-op rather than a duplicate release, and it is mutually exclusive with the milestone hand-off so a run can never both publish and continue.
Show the publish pipeline
09

Surviving 16 weeks: context, crashes, and money

WhatEach milestone runs as its own durable run with a token budget; when it is exhausted, the campaign hands off to a fresh run carrying its state forward. Everything else stops loudly for a human.
WhyAgents degrade as their context fills, so a months-long campaign cannot be one enormous conversation. But an automatic retry-everything loop is worse: an earlier draft of this workflow turned a deliberate budget denial into an infinite, self-funding loop.
HowThe error boundary catches exactly one error code — token-budget exhaustion — and only that one continues as a new run. Because the engine copies completed work into the successor run, nothing is redone. Denials and real failures terminate.

07Status, and the parts that are still wrong

Ferric has not been launched. The workflow is written and renders cleanly across every milestone; the first run would execute M0 only and stop at the boundary-POC gate. Nothing has been ported, and no benchmark exists.

Workflow authored & graph-verified 12 verified critical defects open 0 lines of React ported

The workflow itself was produced adversarially. Five agents wrote it independently and blind, five more audited those attempts against a fixed rubric, and the best ideas were fused into the version documented here. That fused version was then handed to a second blind round — four models reviewing it independently, a blind judge merging their findings — which returned twelve verified critical defects in the code on this page. A selection:

Publishing known holes before launch is deliberate, and so is publishing the count going up rather than down. A project whose entire pitch is “someone else's tests decide whether we are lying” does not get to be shy about its own bugs. The full fused review, every lane's independent report, and the scoring are archived alongside the campaign.

A measured aside from that round: a lane built a WebAssembly harness and put the boundary crossing cost at roughly 3–4.5ns, about 0.017ms of tax on a 5,461-crossing update — under 2% of a frame budget. That is the first real evidence that call overhead alone is not what would sink this, which makes an M3 red genuine signal rather than measurement noise.

08Questions people actually ask

Is this affiliated with React or Meta?

No. It is unofficial, ships under its own package names, and never publishes under upstream ones. React is a trademark of Meta.

Will it be faster?

Unknown, and deliberately unclaimed. The benchmark contract — workloads, thresholds, sample counts, blinded ordering, two reproductions 24 hours apart — is frozen at M0, before any Ferric number exists. If the numbers miss, the claim is dropped rather than the benchmark rewritten.

Could I drop it into my app?

Not today. The production posture is real work with its own gates: npm aliases, five bundler integration cells, strict-CSP fixtures, a lockstep version train, a symbolicated panic envelope, and rollback in under fifteen minutes. Until those pass, the honest label is “release candidate,” not GA.

Why WebAssembly, given the boundary cost?

That is precisely the question M3 exists to answer with a measurement rather than an opinion. If the boundary economics fail, the documented outcome is a pivot to server-rendering only — where the crossing rate is far lower — or a public closeout. Killing the project is an allowed result.
