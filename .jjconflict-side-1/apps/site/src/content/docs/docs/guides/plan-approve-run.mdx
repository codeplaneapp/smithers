Every launch passes through admission: a plan, an approval decision bound to that plan's digest, and a run. `smthrs up` compresses the three steps into one command; this guide walks them by hand, for when a plan needs review before anything runs. [Flows, actions, and plans](/docs/concepts/flows-actions-plans/) explains the model behind the steps.

## Before you start

- A discovered flow: `smthrs ls` lists the ids.
- A provider credential for the flow's seat. `smthrs doctor` lists the keys it reads.

## 1. Plan the flow

```bash
smthrs plan deploy/status
```

`smthrs plan` resolves the flow from the project registry, compiles its keyed plan, and prints the plan card: the node graph with each node's cache status, the plan digest, and the complete `approval` payload. It never starts a run, never approves anything, and never writes flow events; the payload it prints is inert until you submit it. Pass input as `key=value` pairs or one `--data <json>` document.

To capture the payload for the next steps:

```bash
approval="$(smthrs --json plan deploy/status | jq -c '.approval')"
```

## 2. Read the approval payload

The payload carries `target`, `scope`, and `idempotencyKey`, and the digest inside it is what the grant binds to. Submit it unchanged: an edited payload is a different ask, not an approved one. The card's `nodes` list shows what the launch would do, one entry per keyed node with status `cached` or `run`, so read it before deciding.

## 3. Approve with a scope

```bash
smthrs approve "$approval" --scope run
```

`--scope` says how far the grant reaches:

| Scope | Reaches |
| --- | --- |
| `once` | This ask only. |
| `run` | The whole run. The interactive default, matching what `smthrs up` grants. |
| `remembered` | Every later run. |

The command prints the decision receipt; a plan-level decision answers `Accepted` with no `runId`. It never plans and never launches a run of its own.

## 4. Run the approved payload

```bash
smthrs run "$approval"
```

`smthrs run` launches the flow the payload authorizes and prints the receipt: `Accepted` with the `runId`, or `Parked` when the plan lacks approval. Attached, the command stays until the run settles and exits with the run's terminal status: 0 for `completed`, 1 for `failed`, 130 for `cancelled`, 3 for parked at `waiting-approval`.

If the executor declines the launch (no seat resolved, a capability not granted, or the flow belongs to another host), `run` prints the run's summary and exits 1. `smthrs status <run-id>` shows what such a run waits for.

## 5. Resume a parked run

A run parks at `waiting-approval` in two cases: the payload had no approval when you ran it (exit 3), or the flow asked for approval mid-flight and journaled a `control.approval.requested` event whose `payload` field is the exact argument for `smthrs approve`. The parked run's status card prints the ready-to-paste pair on its `Unblock` line:

```bash
smthrs status <run-id>
```

Approve the payload, then re-drive the parked execution:

```bash
smthrs approve '<payload>' --scope run
smthrs run <run-id> --resume
```

`smthrs resume <run-id>` is an unlisted alias of `run --resume`; both spellings share one implementation.

## 6. Or take the one-command path

When a plan needs no human review, `smthrs up <flow>` plans, approves with scope `run`, and launches in one invocation. It never prompts and never resumes an existing run.

For a launch that outlives the terminal, `smthrs up -d` spawns a detached child process and returns as soon as the child proves the run row is durable, printing the run id and its log file under `.flows/logs/`. [The up reference](/docs/reference/cli/up/) covers the admission handshake, its timeout, and the detached launch document.

## Verify it worked

- `smthrs ps` lists the run with its status.
- `smthrs status <run-id>` prints the diagnosis card; the `Verdict` line reports how the run settled.
- The launch command's exit code matches the terminal status: 0, 1, 3, or 130 as above.
