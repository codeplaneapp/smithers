# Scaffold the workflow files

You are the scaffolder. Turn the approved design into real, runnable Smithers
files. You have file + shell tools: **write the files to disk**, then report
exactly what you wrote. No placeholders, no TODO stubs, no mocked data.

## Provisioning (templates, components, skills, agents available)

{JSON.stringify(props.provisioning, null, 2)}

Write the workflow to {props.workflowsDir} as a `NAME.tsx` file (NAME = the
design's kebab-case workflowName). Write each prompt to {props.promptsDir} as its
own `.mdx` file, one per prompt named in the design. Write the custom UI to
{props.uiDir} as `NAME.tsx`.

## How to write the workflow

1. **Start from the closest example** named in the provisioning manifest. Copy
   its structure, then adapt. Don't invent API; if unsure, re-read the example or
   `bunx smthrs docs`.
2. **Workflow file header**: begin with the seed comments and the JSX pragma,
   exactly like the other workflows in `{props.workflowsDir}`:
   ```
   // smithers-source: seeded
   // smithers-metadata-version: 1
   // smithers-display-name: <Title Case Name>
   // smithers-description: <one sentence: what the workflow does>
   // smithers-tags: <comma-separated tags, e.g. ops, reporting>
   /** @jsxImportSource smthrs */
   ```
3. **Imports**: `import { createSmithers } from "smthrs"` (or
   `import { createSmithers, UI } from "smthrs"` when writing a
   custom UI), `import { z } from "zod/v4"`, `import { agents } from "../agents"`,
   any components from `../components`, and each prompt from
   `../prompts/<name>.mdx`.
4. **Schemas**: define the Zod input schema and one schema per task output.
   Call `createSmithers({ input: inputSchema, <table>: <schema>, ... })` and
   destructure only the components you use (`Workflow`, `Task`, `Sequence`,
   `Branch`, `Loop`, `Approval`, `smithers`, `outputs`).
5. **Graph**: `export default smithers((ctx) => ( <Workflow name="<id>"> ... ))`,
   matching the design's `graphShape`. If writing a custom UI, the first child of
   `<Workflow>` must be `<UI entry="../ui/<workflowName>.tsx" title="<Title>" />`.
   When a task simply consumes one upstream task's output, prefer
   `<Task deps={{ upstreamId: outputs.table }}>` with a `(deps) => ...` prompt or
   compute function over a manual guard. Reach for `ctx.outputMaybe("table", { nodeId })`
   when the gate is structural instead (branches, loops, multiple siblings, or a
   condition that inspects content, not just existence), exactly like the existing
   workflows. Remember: `ctx.input` fields arrive null when unsupplied, so coalesce
   (`ctx.input.x ?? default`) rather than trusting Zod defaults.
6. **Prompts**: author each `.mdx` from the design's `prompts` list. Pass props
   from the task and end every prompt with:
   ```
   REQUIRED OUTPUT:
   {props.schema}
   ```
   `.mdx` prompt files are parsed as MDX modules. Wrap JSX/HTML-like prose examples
   such as `<Parallel maxConcurrency={N}>` in inline backticks or fenced code blocks;
   otherwise MDX treats the example as JSX and can break the default export.
7. **Agents**: only add a new provider/pool to `../agents.ts` if the design
   truly needs one that doesn't exist; otherwise reuse the existing pools.
8. **Skills**: if the design relies on a worker skill the provisioning step
   marked `recommended` (not yet installed), create a concise skill file under
   the local skills dir so the workflow's agents have it.

## Scaffold the custom UI and workflow declaration (required)

Also write `{props.uiDir}/<workflowName>.tsx` implementing the design's `ui`
plan (skip only if the design's `ui` is null because the user declined one):

1. **Copy the shape of an existing UI**: read `{props.uiDir}/vcs.tsx` and/or
   `{props.uiDir}/create-workflow.tsx` first and match their conventions.
2. Start with `/** @jsxImportSource react */`, import React hooks from `react`,
   and import `createGatewayReactRoot`, `useGatewayRuns`, `useGatewayRunEvents`,
   `useGatewayNodeOutput`, and `useGatewayActions` (as needed) from
   `smthrs/gateway-react`.
3. **Compose from the shipped component libraries instead of hand-rolling
   markup or CSS**: `smthrs/gateway-ui` for the run widgets
   (`WorkflowUiShell` as the page scaffold, or `SimpleWorkflowDashboard` when
   launch-and-watch is all the workflow needs, plus `RunList`, `RunTree`,
   `RunEventLog`, `NodeOutputView`, `ApprovalPanel`, `LaunchButton`,
   `ConnectionBadge`, `StatusPill`) and `smthrs/ui` for the
   primitives (`Button`, `Card`, `Input`, `Tabs`, `Table`, `Badge`,
   `StatusPill`, `EmptyState`, `SectionHeader`, `RowButton`, `KpiStat`; render
   `<SmithersUiStyles />` once at the root). Write bespoke JSX only for panels
   neither library covers.
4. Set the workflow key constant to the workflow id and read the runId from the
   URL (`?runId=`), like the existing UIs do.
5. Render the design's `ui.panels` from the real node output tables (the task
   ids and schemas you scaffolded above). Node-output hooks may return the row
   directly or `{ row, schema, status }`, and row fields can be snake_case with
   JSON-string arrays: parse defensively like `vcs.tsx` does.
6. Mount with `createGatewayReactRoot(...)` at the bottom, matching the
   existing UIs.
7. Make sure the workflow imports `UI` and declares
   `<UI entry="../ui/<workflowName>.tsx" title="<Title>" />` inside the root
   `<Workflow>`. Do not register the UI in `.smithers/gateway.ts`.
8. Verify it transpiles before you finish:
   `bun build --no-bundle {props.uiDir}/<workflowName>.tsx > /dev/null`.

## Scaffold the monitor workflow

A **monitor** is a workflow that watches this one while it runs. Smithers
launches `{props.monitorDir}/<workflowName>.tsx` automatically, as a sibling run
linked to the watched run, whenever `<workflowName>` starts. Zero monitor files
means zero behavior change, so this is opt-in per workflow.

Write `{props.monitorDir}/<workflowName>.tsx` when the workflow runs long,
unattended, in the background, or loops - the cases where it can silently wedge
and nobody notices. Skip it for short interactive workflows, and never write a
monitor for a monitor.

Compose the shipped `Monitor` component rather than hand-rolling a poll loop:

```tsx
/** @jsxImportSource smthrs */
import { Monitor, createSmithers } from "smthrs";
import { z } from "zod/v4";
import { agents } from "../agents";

const { Workflow, smithers, outputs } = createSmithers({
  health: z.object({
    condition: z.enum([
      "healthy", "stalled", "wedged-node", "runaway-loop", "awaiting-human", "failing", "unknown",
    ]),
    runStatus: z.string(),
    targetNodeId: z.string().nullable().default(null),
    evidence: z.string(),
    summary: z.string(),
  }),
  action: z.object({ action: z.string(), changed: z.boolean().default(false), summary: z.string() }),
});

export default smithers((ctx) => (
  <Workflow name="<workflowName>-monitor">
    <Monitor
      watchRunId={ctx.input.watchRunId}
      agent={agents.cheapFast}
      healthOutput={outputs.health}
      actionOutput={outputs.action}
      intervalMs={60_000}
    />
  </Workflow>
));
```

Rules: `nodeId`/`runId`/`iteration` are reserved output columns, so the
implicated node field must be `targetNodeId`. The monitor receives
`watchRunId`, `watchWorkflowId`, and `watchWorkflowPath` as input. It reads run
state through `smthrs/gateway-client` or the public CLI, never
the store. Leave `autoHeal` at its default (`stalled`, `wedged-node`) unless the
design says otherwise: those two repairs are idempotent and reversible, and
everything else escalates to a human.

## Scaffold the workflow's test (required, not optional)

A workflow and its tests are **one indivisible change**. A workflow without a
registered test is unfinished work, and verification will fail on it — so write
the test in the same pass, never as a follow-up.

1. Write `{props.testsDir}/<workflowName>.test.tsx`. Import the **real**
   workflow module and drive it through `renderWorkflow` from
   `smthrs/testing`. A hand-built plan/graph object validates a
   stand-in that merely resembles the workflow and passes while the real file is
   broken.
2. **Register it**: append `./tests/<workflowName>.test.tsx` to the
   space-separated `test` script in `{props.packageJson}`. That list is not a
   glob — preserve every existing path and add yours at the end. An unregistered
   test is silently never run.
3. Assert real graph behavior. The floor is four assertions:
   - the expected node ids are present;
   - their expected order / `dependsOn` edges hold;
   - each task's `outputSchema` accepts a representative value and rejects a
     malformed one (`schema.safeParse(value).success`);
   - branches and loops render the right nodes for the inputs that drive them.

   `expect(graph).toBeTruthy()` is not a test; it will be treated as a missing
   one.

```tsx
import { describe, expect, test } from "bun:test";
import { join } from "node:path";
import { renderWorkflow } from "smthrs/testing";
import workflow from "../workflows/<workflowName>.tsx";

const workflowPath = join(import.meta.dir, "..", "workflows", "<workflowName>.tsx");

describe("<workflowName>", () => {
  test("renders the expected graph", async () => {
    const graph = await renderWorkflow(workflow, { workflowPath, input: { /* … */ }, outputs: {} });
    expect(graph.tasks.map((task) => task.nodeId)).toEqual(["first", "second"]);
    expect(graph.tasks.find((task) => task.nodeId === "second")?.dependsOn).toContain("first");
    const first = graph.tasks.find((task) => task.nodeId === "first");
    expect(first?.outputSchema.safeParse({ /* representative valid value */ }).success).toBe(true);
    expect(first?.outputSchema.safeParse({ /* representative malformed value */ }).success).toBe(false);
  });
});
```

Run it before you finish (the `./` prefixes matter: bun treats a bare argument
as a name filter and would silently match no files):
`bun test --preload ./{props.preload} --max-concurrency=1 ./{props.testsDir}/<workflowName>.test.tsx`

## Acceptance criteria

- `bunx smthrs graph {props.workflowsDir}/<workflowName>.tsx`
  exits 0 (run it yourself before finishing).
- `{props.testsDir}/<workflowName>.test.tsx` exists, is registered in
  `{props.packageJson}`, and passes.
- If you wrote a monitor,
  `bunx smthrs graph {props.monitorDir}/<workflowName>.tsx`
  exits 0 too.
- The UI file (when required) transpiles with `bun build --no-bundle`.
- The workflow declares the UI with `<UI entry="../ui/<workflowName>.tsx" />`;
  no `gateway.register(..., { ui })` snippet is added.
- Every file in the design's `prompts` and `ui` lists exists on disk.
- Style matches the neighbouring files; no dead code.
