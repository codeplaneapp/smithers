## Judge

1. **Boundary correctness** — does every path's destination lane make sense
   given its actual imports and callers? Flag any path that looks misassigned.
2. **Ambiguous shared utilities** — code imported by 2+ destination lanes that
   isn't cleanly ownable by one lane. Each needs a call: duplicate it, promote
   it to `stays-in-smithers` as a published dependency, or pick one owning
   lane and have the others depend on it post-publish.
3. **Publish ordering** — does the DAG's edge set correctly force upstream
   lanes to publish before downstream lanes decouple against them? Flag any
   missing edge or cycle.
4. **License coverage** — does every extracted lane's manifest entries carry
   forward a LICENSE, and is the license consistent with the monorepo's?
5. **Release plan soundness** — does `release-plan.json` model every one of
   the 10 new repos with ZERO, ONE, or MANY publishable packages (correct
   paths/names/versions), are the per-package repository dependencies real and
   consistent with `dag.json`, and are GitHub-release-only repos (e.g.
   examples/apps) marked as such rather than force-fit into an npm publish?
6. **History-merge lanes** — are the source-owned browser-UI paths (multi)
   and hosted control-plane / electric-proxy paths (plue) completely and
   correctly identified in the manifest, and is awesome-smithers docs-only?
7. **Risks** — anything else that would break a lane's standalone build,
   cause a stale doc link, or block a clean history-preserving extraction.
