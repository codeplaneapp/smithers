Rough guide to what each is for:

- `implement` — build a feature or change from a clear ask, with review.
- `research-plan-implement` — research, then plan, then implement end-to-end.
- `review` — review a specific diff or change before landing it.
- `plan` — produce a plan or design without building yet.
- `research` — gather and synthesize information about a topic.
- `grill-me` — adversarially stress-test an idea, plan, or PRD with hard questions.
- `ralph` — long-running autonomous loop that keeps working until a goal is met.
- `debug` — investigate and fix the root cause of a defect in the user's own code.
- `audit` — read-only sweep of a feature, surface, or area; deliverable is findings, not fixes.
- `create-workflow` — author a brand-new Smithers workflow from a description.
- `context-doctor` — diagnose and repair an agent's working context.
- `monitor-smithers` — watchdog that detects stuck, blocked, failed, or over-budget runs.
- `triage-run` — diagnose one failed or stuck Smithers run and recommend fix, rewind, retry, or escalate.
- `report-slideshow` — turn a finished run into a self-contained HTML slideshow report.
- `eval-author` — turn acceptance criteria into a runnable eval suite.
- `create-skill` — author a new reusable agent skill.
- `extract-skill` — harvest a reusable skill or workflow sketch from a finished run.
- `improve-test-coverage` — raise test coverage until a target holds.
- `hodge-counterexample-search` — run a scoped, parallel, independently verified search for Hodge-conjecture counterexample candidates.

## Tie-breaking

Prefer the most SPECIFIC workflow that covers the ask over a general one:

- Diagnosing a failed or stuck **Smithers run** goes to `triage-run`, not
  `debug` — `debug` is for defects in the user's own code.
- A read-only findings sweep is `audit`; reviewing a specific diff is `review`.
- Ongoing watching of many runs is `monitor-smithers`; one run's post-mortem is
  `triage-run`.
- Hodge-conjecture counterexample searches go to `hodge-counterexample-search`,
  not generic `research`, when the user wants candidate generation plus verification.
- If two workflows fit equally, pick the narrower one and list the broader one
  in `alternativeWorkflows`.

## Produce

1. `recommendedWorkflow` — the single best-fit id from the list. Prefer the
   classifier's `recommendedWorkflow` when it is sound; override it only if a
   different listed workflow clearly fits better.
2. `why` — why this workflow fits the task, naming the durable behaviour it
   provides (ordering, recovery, approval, or loops) that the task needs.
3. `alternativeWorkflows` — other listed ids that could also fit, best-first; an
   empty array if nothing else is a reasonable second choice.
