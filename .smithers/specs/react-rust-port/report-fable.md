### F2 — The entire suite runs under jest legacy fake timers, and internal act() requires them

- `scripts/jest/config.base.js:33-36`: `fakeTimers: {enableGlobally: true, legacyFakeTimers: true}` — **every test file**, both source and build mode, has `setTimeout`/`setInterval`/`setImmediate` mocked. Only 10 files call `jest.useFakeTimers` explicitly (they re-configure, e.g. `SchedulerSetTimeout-test.js`); the global config is what matters — per-file greps undercount by design.
- `packages/internal-test-utils/internalAct.js:66-71`: `act` **throws** unless `jest.isMockFunction(setTimeout)` — fake timers are a hard precondition of the whole assertLog/waitFor machinery. It also calls `jest.getTimerCount()`, `jest.runAllTicks()`, `jest.runOnlyPendingTimers()` (internalAct.js:133-141, 212-220) to force Suspense fallback timers.
- The harness escapes fake timers for real macrotasks via `node:worker_threads` MessageChannel: `packages/internal-test-utils/enqueueTask.js:10-20`. Separately, `scripts/jest/patchMessageChannel.js` replaces global `MessageChannel` with a **setTimeout-backed (i.e. fake-timer-controlled)** one, used by 20+ Fizz/Flight browser tests.

**Bridge constraint:** any JS host shim in the Ferric glue that schedules with `setTimeout`/`MessageChannel` is *inside* the mocked-timer world in tests. Timing must flow through the same host seams React uses (Scheduler host callbacks; `enqueueTask`-style escape only where React itself escapes), never through ad-hoc glue timers, or tests hang or fire out of order.

### F3 — In build mode the whole suite runs on `scheduler/unstable_mock`, and the scheduling seam is a swappable JS module boundary (the strongest single harness constraint)

- `scripts/jest/setupTests.build.js:3`: `jest.mock('scheduler', () => jest.requireActual('scheduler/unstable_mock'))` — for **every build-mode test**, any `require('scheduler')` resolves to the mock artifact (`config.build.js:44-50` maps both `scheduler` and `scheduler/unstable_mock` to `build/<channel>/scheduler/*`).
- The reconciler consumes the scheduler **exclusively through a JS import**: `packages/react-reconciler/src/Scheduler.js` re-exports `unstable_scheduleCallback/cancelCallback/shouldYield/requestPaint/now/getCurrentPriorityLevel`, priority constants, plus the mock-only `log` and `unstable_setDisableYieldValue`. In the rolled-up `react-dom` artifact the scheduler stays an external `require('scheduler')`.
- Individual tests substitute **their own hand-written JS schedulers**: `ReactSchedulerIntegration-test.js:200`, `ReactART-test.js:31`, `ReactProfiler-test.internal.js:132`.

**Consequence (refines the fused plan):** the fused plan's "M2: priority heaps and timing in Rust; MessageChannel host stays a ~200-line JS shim" is necessary but not sufficient. The constraint is stronger: **in the oracle artifacts, the reconciler must dispatch every `scheduleCallback` / `shouldYield` / `now` / `log` through the `require('scheduler')` module boundary in JS**, because jest swaps that module identity per test (global mock, per-test custom mocks). A Rust reconciler that short-circuits to its sibling Rust scheduler inside the same wasm instance will pass `scheduler`'s own tests and silently stop being judged by every other test — exactly the falsifiability hole `REACT_RUST_ASSERT_BACKEND` exists to prevent. The Rust work loop therefore calls out through glue for `shouldYield()`/`now()` per unit of work — which is fine, because upstream React already pays a JS call per unit at exactly those points (`ReactFiberWorkLoop.js:3059-3065`, `3042-3056`).

### F5 — Measured WASM instantiation costs ⇒ fresh-Instance-per-reset is affordable; strategy decided

Measured on this machine (Node v24.12.0, M-series; generator script shown in §4.3 note):

| Synthetic module | sync `new WebAssembly.Module` (first, uncached) | `new WebAssembly.Instance` (Module cached) | compile+instantiate (V8 dedup-cached bytes) |
|---|---|---|---|
| 1.80 MB, 10k funcs | 1.8 ms | **38 µs** | 0.4 ms |
| 5.39 MB, 30k funcs | 5.1 ms | **135 µs** | 1.0 ms |

Caveat stated honestly: synthetic repeated-function bodies compile faster than real wasm-bindgen output; budget 5-30 ms/MB for a first Liftoff compile of real code. Cost math against F1's denominator:

- **Fresh Instance per registry reset, Module cached:** 16,000 × ~0.1 ms ≈ **1.6 s total** across the whole 4-config run (before jest's ~14-way worker parallelism). Noise.
- **Module compiled once per test-file realm** (file-scope cache in the glue; jest gives each test file its own jsdom realm but `resetModules` re-evaluates modules *in the same realm*): 262 files × 4 configs × ~10-30 ms ≈ **10-30 s total**, ÷ workers ≈ 1-2 s wall. Acceptable even without cross-file caching.
- **Nothing cached (worst case):** 16,000 × 30 ms ≈ 8 min ÷ 14 workers ≈ 35 s wall — degraded but not fatal. The strategy cannot "silently die"; it can only get ~1 minute slower.

Two structural notes that make fresh-Instance *mandatory*, not just affordable: (a) `ReactFlight-test.js` holds **two module registries alive in one test** (F12) — an engine-singleton design is wrong, not just slow; (b) test isolation is the falsifiability story — `engine_reset()` state-wipes are exactly the kind of "shared state between tests" a hostile reviewer would probe. Decision D1.

Memory: each Instance's linear memory is GC'd with its registry; jest already retains per-file registries of ~500 KB JS bundles today. Watch RSS with `--logHeapUsage` at M0; keep initial memory small and grow.

### F6 — Stack-depth reality: client render loop is iterative; commit and Fizz are recursive (verified)

- **Client render loop: iterative.** `workLoopSync` (`ReactFiberWorkLoop.js:2758-2763`) is `while (workInProgress !== null) performUnitOfWork(...)`. `workLoopConcurrent(nonIdle)` (`:3042-3056`) is the same loop with a 25 ms/5 ms time budget via `now()`; `workLoopConcurrentByScheduler` (`:3059-3065`) checks `shouldYield()` per unit. Begin/complete walk fiber `return` pointers, not the JS stack. **⇒ JS↔wasm nesting depth for a render is O(1) per entry, not O(tree depth).**
- **Commit phase: recursive over tree depth.** `recursivelyTraverseMutationEffects` (`ReactFiberCommitWork.js:2016`) and its layout/passive/double-invoke siblings (`recursivelyTraverseAndDoubleInvokeEffectsInDEV`, `ReactFiberWorkLoop.js:5296`) recurse child-by-child, interleaving user callbacks with host mutations in tree order.
- **Fizz: recursive over element depth.** `renderNode` (`react-server/src/ReactFizzServer.js:4244`) snapshots 8 task-context fields, calls `renderNodeDestructive` (`:3407`) → `retryNode` (`:3437`) → `renderElement` (`:2996`) → user component → back into `renderNodeDestructive`/`renderChildrenArray` (`:3881`), ~4-5 native frames per JSX depth level, with a per-level `catch` that restores `formatContext`/`keyPath`/`treeContext`/componentStack on suspension (`:4244-4290`).

**Wasm stack budget implication.** V8 gives wasm calls the same ~1 MB native stack JS gets, and the oracle runs under React's *own* jest configs — we cannot add `--stack-size`/`NODE_OPTIONS` without weakening the "unmodified suite" claim (and real users' jest won't have them either). JS burns ~100-200 B/frame; Rust frames are routinely 2-5× that. A mirrored-recursion Rust Fizz would overflow at roughly ¼-½ the tree depth upstream survives — a class of failure the suite *will* find (`ReactDOMFizzServer-test.js` alone is 168 cases). **Decision D3: Rust ports of Fizz rendering and the commit traversals are iterative with explicit heap-allocated frame stacks; per-level restore-on-throw semantics move into explicit frame pops.** Hard spec requirement, not a style choice.

### F8 — PROD builds replace `global.Error` with a decoding Proxy; Rust errors must be born as sandbox JS Errors

`scripts/jest/setupTests.js:86-180`: in PROD runs the harness installs an `ErrorProxy` over `global.Error` that decodes `react.dev/errors/<code>` URLs back into full messages via `scripts/error-codes/codes.json`, and proxies instances. Implications:

1. Every Rust-originated throw must surface as `new Error(...)` executed **in the jest sandbox realm** by the glue (the sandbox's `Error` *is* the proxy), carrying the exact minified-URL format upstream emits, with codes present in `codes.json`. String-building in Rust, construction in JS.
2. A wasm **trap** surfaces as `WebAssembly.RuntimeError` constructed by the engine — it bypasses the proxy, decodes to nothing, and reads as gibberish in 4,000+ PROD assertions. Traps must never be a semantic path (Decision D6: panic = engine-poisoned; glue converts to a distinguishable `FerricInternalError`; under `REACT_RUST_ASSERT_BACKEND` any poisoning fails the test).

### F9 — The commit is an interruptible 8-state machine, not an atomic buffer drain

`ReactFiberWorkLoop.js:730`: `pendingEffectsStatus: 0..7` with explicit phases — `flushMutationEffects` (`:3995`), `flushLayoutEffects` (`:4041`), after-mutation/spawned-work (`:3984-4151`), passive (`:780-786`, flushed early at `:1896` if a new render starts first). Between phases React returns to the platform. Additionally the commit can **park before mutating anything**: `completeRootWhenReady` (`:1564`) → `startSuspendingCommit`/`suspendResource`/`waitForCommitToBeReady` (`react-dom-bindings/src/client/ReactFiberConfigDOM.js:6367/6424/6536`) — commit waits for stylesheets while *new renders proceed*. And `root.current = finishedWork` is flipped mid-machine, precisely between mutation and layout (`:4033-4038`).

**⇒ the bridge's "phase-bounded command buffers" (fused plan) are confirmed as the right shape, but the contract must be one buffer *per pendingEffectsStatus phase*, with engine state persisting a ready-to-commit tree across JS turns, and the current/finished flip as an explicit engine transition between the mutation and layout buffers.** A single "commit → drain everything" export cannot express suspended commits, interleaved passive flushes, or the reentrancy in scenarios S5/S7.

### F10 — Two infinite-loop guards, one of which we lose

- The babel transform `transform-prevent-infinite-loops` (`scripts/jest/preprocessor.js:20`) guards **source and test files only** — build artifacts are transform-ignored (`config.build.js:70`). Upstream's compiled JS can still hang; a wasm engine hang additionally blocks the worker's event loop so jest's 5 s timeout never fires → worker kill, opaque CI red. Ferric dev builds need an internal work-loop fuel counter (DEV-only) that throws a JS error instead of spinning.
- The *semantic* guard must be ported exactly: `NESTED_UPDATE_LIMIT = 50` (`ReactFiberWorkLoop.js:749`) and the "Maximum update depth exceeded" throws (`:5201-5243`) are asserted by tests.

### F11 — `@gate` flags are read from source truth, not from the artifact

`config.build.js:40-41` maps `shared/ReactFeatureFlags` → `shared/forks/ReactFeatureFlags.readonly`, which `require`s the **source** `ReactFeatureFlags.js` and freezes it. So gate predicates (`scripts/jest/setupTests.js:245-304`, `TestFlags.js`) evaluate against source-truth flag values while the artifact runs its compiled-in values. If Ferric's flag codegen drifts one flag from the pinned SHA's source, gates mispredict and tests fail in *both* directions (`[GATED, SHOULD FAIL]` inversions — `setupTests.js:262-268`). This is why the fused plan's fail-closed flag codegen is load-bearing, and it gives the mechanical check: codegen input = the same file the readonly fork reads.

### F12 — Flight tests hold two live registries in one test; the engine cannot be a per-process singleton

`ReactFlight-test.js` calls `jest.resetModules()` 13 times **inside test bodies** to simulate server and client with different module states in a single test. Element brands survive because React uses `Symbol.for` (registry-global). Contract: each glue evaluation binds its own engine instance; cross-instance element recognition happens via `Symbol.for` brands and plain-object shape, exactly as upstream artifacts behave. Any process-global engine state is a correctness bug, not just a perf choice.

### F13 — Remaining `scripts/jest/` inventory read for constraints (nothing else blocks)

- `ReactJSDOMEnvironment.js` — thin subclass of `jest-environment-jsdom` adding document readyState control; `WebAssembly` is available in the sandbox (V8 context global). Verify at M0 with a one-line canary, then rely on it.

- `spec-equivalence-reporter/` — only active under `REACT_CLASS_EQUIVALENCE_TEST` (`setupTests.js:11-14`), a separate class-semantics harness not in the 4 oracle legs. Out of scope; noted so it isn't "discovered" later.

## 2 · DECISIONS

**D1 — WASM instantiation strategy for jest: fresh `WebAssembly.Instance` per module-registry evaluation; `WebAssembly.Module` compiled once per test-file realm and cached at glue file scope; optional process-wide cache via the shared `process` object verified at M0.**
Why: F1 (16k resets), F5 (38-135 µs/instance measured; worst-case uncached ≈ +35 s wall on the whole run), F12 (two live registries in one test make singletons semantically wrong), falsifiability (fresh state per test is un-attackable).
Fallback if real-world numbers betray the synthetic bench (>10 ms per reset measured in M0): single Instance per file + `ferric_reset()` export that rebuilds all engine state and zeroes the JS handle table, gated by an M0 differential run proving no cross-test leakage on 3 consecutive full-suite runs. The fallback is a *performance* valve only; it is never taken for memory-correctness reasons.

**D2 — The scheduling seam stays a JS module boundary in every oracle artifact.** Rust owns heap/lane math *behind* `scheduler`'s exports; the reconciler engine requests scheduling exclusively through glue that calls the ambient `require('scheduler')` module (F3). `shouldYield`/`now` crossings per unit of work are accepted — upstream pays the same call at the same points. The M2 "hidden gate" (whole suite on the Rust mock) is only honest under this seam.

**D3 — Iterative-by-construction for every recursion that scales with tree depth: Fizz render (`renderNode` chain), commit traversals, DEV double-invoke walks.** Explicit heap frame stacks; per-level context restore (F6's `renderNode` catch) becomes frame-pop restore. The work loop is already iterative (F6), so this touches only Fizz + commit. Rationale: 1 MB default stack under React's own jest configs, no flag escape hatch without weakening the claim.

**D4 — Exceptions never cross the ABI raw.** Every JS→wasm export and every wasm→JS import returns/receives a tagged status `{code: u32, payload: u32}`; JS user-code invocations are wrapped by glue `try/catch` that reifies the thrown value into a handle; Rust never observes a foreign unwind (which would skip `Drop` and corrupt engine invariants), and JS never observes a wasm trap on a semantic path (F8). React's own `handleThrow`/`throwException` (`ReactFiberWorkLoop.js:2806-2860`, `ReactFiberThrow.js:364`) become engine transitions on the reified value.

**D5 — MODULE_QUEUE semantics: dependency-ordered *rows* for the 22 out-of-cycle modules; cohort-slice rows (fused a-f) for the 59-module SCC, each gated by the TSV's test mapping; the reconciler crate lands atomically per cohort through one merge queue.** The TSV is regenerated by the committed script (§4.4) at every rebase; a row-set diff is a gate input.

**D6 — Panic policy: `panic = "abort"`; a trap marks the instance poisoned; glue throws `FerricInternalError` carrying the last engine breadcrumb; `REACT_RUST_ASSERT_BACKEND=1` turns any poisoning into a test failure.** DEV builds carry a work-loop fuel guard (F10) so hangs become errors, not worker kills.

**D7 — Command buffers are phase-scoped to `pendingEffectsStatus` transitions (F9), with five buffer classes: before-mutation (snapshot+selection reads), mutation, ref-detach/attach, layout, passive — and an explicit engine transition for the `root.current` flip between mutation and layout.**

## 4 · SPEC TEXT (ready to lift)

### 4.1 `BRIDGE.md` v0 — crossing-scenario contracts

*Terminology: "engine" = the Rust/wasm core; "glue" = the JS in our artifacts; "handle" = u32 generational JsRef; "trampoline" = glue function the engine calls to run user code. All entry/exit rules assume D4 (tagged results, no raw unwinds). Each scenario: semantics anchor (upstream source) → bridge contract.*

**S1. Adversarial child intake — throwing getters, hostile iterators.**
Anchor: `react-reconciler/src/ReactChildFiber.js:1380-1417` (`getIteratorFn`, `iteratorFn.call`, the `entries === iteratorFn` re-iteration warning), `:2040-2070` (outer catch).
Contract: `scanChildSet(resultHandle, scratchPtr)` walks the returned child value in React's exact traversal order, reading `$$typeof`/`type`/`key`/`props` exactly once each, at the same points upstream reads them. Any user throw during the scan aborts the scan with `{code: SCAN_THREW, error: handle, scannedCount}`; the engine treats it exactly as a component-body throw at that fiber (→ S10). The scratch buffer's committed prefix is the only state; no partial fiber is created. Differential test: the suite's own iterator tests plus fuzzed getters/iterators that throw at index k.

**S2. Thenable or `lazy` encountered *during* child scan (scan-time suspension).**
Anchor: `ReactChildFiber.js:288` (`trackUsedThenable` from the scan path), `ReactFiberThenable.js:316` (`resolveLazy` throws the payload thenable when pending), `ReactChildFiber.js:2056-2058` (SuspenseException passthrough).
Contract: the scan calls back into the engine's thenable tracker (`noteUsedThenable(index, thenableHandle)`), which returns a resolved-value handle or signals suspend. Scan-time suspends surface as `{code: SCAN_SUSPENDED, thenable: handle}`; the engine records its `workInProgressSuspendedReason` equivalents. The thenable-state array for the fiber lives in JS (values are user objects) keyed by engine fiber id, preserved across replays (→ S3).

**S3. Component throws a thenable mid-render (`use`, throw-promise) and replay.**

**S5. Sync `setState` from an event listener while the mutation buffer is mid-drain.**
Anchor: `ReactFiberHooks.js:3614` (`dispatchSetState`); React pre-arms against this by disabling its event emitter and saving selection before any mutation — `prepareForCommit` (`ReactFiberConfigDOM.js:420-431`), re-enabled in `resetAfterCommit` (`:453-458`) called at the end of `flushMutationEffects` (`ReactFiberWorkLoop.js:4024`); commit runs under `executionContext |= CommitContext` (`:4015`).

Contract: `ferric_flush_sync_work()` export returns `{flushed: bool, wasInRenderOrCommit: bool}`; glue reproduces the DEV `console.error` byte-identically from `warnings.rs` text. The update itself is still recorded (priority bump to Discrete happened in JS before the call) — only the *flush* is skipped, exactly as upstream.

**S7. `flushSync` from a passive effect while the passive drain is mid-list.**
Anchor: passive flush is itself an entry (`pendingEffectsStatus === PENDING_PASSIVE_PHASE`, `ReactFiberWorkLoop.js:780-786`; early flush at `:1896`); flushSync from inside it is legal and flushes (passive flush does not set RenderContext).
Contract: nested bridge frame — passive drain (depth 1) → effect trampoline (JS) → flushSync → render+commit (depth 2) → return → drain continues at the recorded list index. Engine passive-drain state (current list cursor) must be reentrancy-safe: stored per drain-frame, not in a single global cursor.

**S8. Multiple concurrent roots; cross-root sync work.**

Contract: the engine holds the root registry; every root created by glue registers `(rootHandle ↔ containerHandle)`. `ferric_flush_sync_across_roots(onlyLegacy)` iterates engine-side. **S9. Selection save/restore and `getSnapshotBeforeUpdate` ordering relative to mutation batches.**
Anchor: `commitBeforeMutationEffects` (`ReactFiberCommitWork.js:343`) → `prepareForCommit` saves selection + disables events (`ReactFiberConfigDOM.js:420`); `getSnapshotBeforeUpdate` invoked per-fiber in the before-mutation walk (`ReactFiberCommitEffects.js:632`); `resetAfterCommit` restores selection *after* the mutation buffer, *before* layout (`ReactFiberWorkLoop.js:4024`, current-flip at `:4033-4038`).

The engine may never fuse before-mutation reads into the mutation buffer — reads must complete before the first write (the buffer split is a *correctness* boundary, not an optimization).

**S10. Error-boundary unwind when the throw crosses JS→Rust→JS.**
Anchor: `ReactFiberThrow.js:364` (`throwException`), value classification, `ReactFiberWorkLoop.js:2817-2827` (`SuspendedOnError` unwind path).
Contract: user throw → reified handle (D4) → engine classifies (thenable? sentinel? plain error) → engine performs the unwind over *fibers* (its own structures, no JS stack involved) → boundary found ⇒ trampoline `callGetDerivedStateFromError(handle)` / `callComponentDidCatch(handle, errorInfoHandle)` with **the original JS value by identity** (tests assert `===` on caught errors). `errorInfo.componentStack` is produced by the JS debug helper from the engine's fiber-path query (names must be real JS function names — F13).

**S11. A layout effect or ref callback throws mid-commit; the commit must finish.**
Anchor: per-callback guards — `safelyDetachRef` (`ReactFiberCommitEffects.js:842`), `captureCommitPhaseError` usage throughout CommitEffects/CommitWork.
Contract: executor wraps each user-callback op in try/catch; a throw is pushed to the engine's commit-error queue `(fiberHandle, errorHandle)` and the drain continues with the next op. After the phase's buffer completes, the engine schedules boundary work from the queue exactly where upstream calls `captureCommitPhaseError`. The buffer format therefore marks which ops are user-callback ops (catchable) vs host ops (a DOM throw follows upstream's behavior: it propagates — upstream does not guard `appendChild`).

**S12. Ref detach/attach ordering, including ref cleanup functions.**
Anchor: detach during mutation before unmounts (`ReactFiberCommitEffects.js:842`), attach during layout (`:757`); function refs may return cleanup functions (handled in `commitAttachRef`).
Contract: `RefDetach(fiberHandle, refHandle)` ops in the mutation buffer, `RefAttach(fiberHandle, refHandle, instanceNodeId)` in the layout buffer, in exact traversal order. Glue stores returned cleanup functions in the ref-record (JS side) keyed by fiber id; the next detach op invokes cleanup instead of `ref(null)` when present — semantics live in glue, *ordering* lives in the engine's buffer emission.

**S13. `act()` — sync and async environments.**
Anchor: `ReactFiberRootScheduler.js:157, 469, 630-657` — when `ReactSharedInternals.actQueue !== null`, React pushes scheduler callbacks into the act queue instead of the real scheduler; internal act drives `SchedulerMock` flush loops + jest fake timers (`internalAct.js:116-157`).
Contract: all engine scheduling exits through one glue chokepoint `scheduleEngineTask(priority, taskId)`; that chokepoint (JS) checks `ReactSharedInternals.actQueue` and either pushes an act-queue closure or calls `Scheduler.unstable_scheduleCallback` — the engine never knows which. This single seam simultaneously satisfies F3 (module swap), act, and the public `act` (`react` package, stays JS untouched).

**S14. `useSyncExternalStore` tearing checks at the commit gate.**
Anchor: `ReactFiberHooks.js:1823` (`pushStoreConsistencyCheck`), `ReactFiberWorkLoop.js:1689-1730` (`isRenderConsistentWithExternalStores` walks `StoreConsistency`-flagged fibers, re-invokes `getSnapshot`, `Object.is`-compares before commit).
Contract: engine keeps the flagged-fiber set; before commit it issues one batched trampoline `checkStoreConsistency(packedPairsPtr, n)` — glue loops `(getSnapshotHandle, prevValueHandle)` pairs, returns first-inconsistent index or -1. Inconsistent ⇒ engine discards and re-renders sync (upstream behavior). One crossing per commit-gate, not per store.

**S15. Hydration mismatch recovery.**
Anchor: `ReactFiberHydrationContext.js:388` (`throwOnHydrationMismatch` with collected diff), `:482-513` (text/instance mismatch sites); recoverable-error queueing and client-render fallback.
Contract: the hydration cursor (nextHydratableInstance walking real DOM) lives in glue; the engine drives it with per-host-fiber queries (`tryHydrateInstance(fiberDescPtr) → nodeId | MISS`) — upstream already pays a host-config call per node here, so parity chatter is accepted. On MISS the *engine* takes the hydration-error path (error string built from the JS-side diff collector via one trampoline), unwinds to the boundary/root, and re-renders client-side; recoverable errors accumulate as handles and are delivered via `onRecoverableError` at commit end (`ReactFiberErrorLogger.js:123`).

**S16. Event replay before hydration completes.**
Anchor: `react-dom-bindings/src/events/ReactDOMEventReplaying.js:228` (`queueIfContinuousEvent`), `:207/:408` (`attemptContinuousHydration`), `:454` (`replayUnblockedEvents`).
Contract: the replay queues are pure JS (events stay JS in v1). The bridge exposes `ferric_attempt_hydration(fiberHandle, laneHint)` and a "boundary became hydrated" JS callback the engine fires at commit, which unblocks queued replays. No event object ever crosses; only fiber handles and lanes.

**S17. Passive-effect flush timing vs microtasks.**
Anchor: root scheduling prefers microtasks (`ReactFiberRootScheduler.js:663-670` `supportsMicrotasks`/`scheduleMicrotask`), then scheduler tasks; passive flush rides a NormalPriority scheduler callback and is force-flushed at the start of a new render if still pending (`ReactFiberWorkLoop.js:1896`); tests advance the world one *real* macrotask at a time via worker-thread MessageChannel (`enqueueTask.js`) — so ordering between microtask root-processing, scheduler-mock flushes, and passive flushes is fully observable.
Contract: the engine never schedules anything itself. `processRootSchedule` equivalents run inside glue-registered microtask callbacks (`queueMicrotask` from the sandbox realm); passive flush is entered only via the S13 chokepoint or the render-entry force-flush. Any engine-internal deferral (e.g. "do it on next export call") is forbidden — it would be invisible to `waitForMicrotasks()` and desequence `assertLog` traces.

**S18. Portals crossing containers.**

Contract: `createPortal` glue registers the container node → `containerHandle`; portal fibers carry it; command-buffer placement ops carry an explicit `containerNodeId` so the executor never infers parents. The JS event layer's ancestry queries (`ferric_get_parent_fiber`) walk the *fiber* tree so bubbling crosses portal boundaries exactly as upstream.

**S19. Nested renderers: Fizz inside a client render, client render inside Fizz completion, renderer-in-renderer tests.**
Anchor: Fizz `Request` is self-contained state (`ReactFizzServer.js` task/request model); reconciler roots are registry entries (S8).
Contract: engine state is partitioned per root and per request; the bridge-frame stack (§4.2) allows Fizz `performWork` to be entered while a fiber work loop is on the JS stack below it and vice versa. **S20. Fizz stream pull, backpressure, and abort.**

The resume callback enters through a dedicated export `ferric_commit_when_ready(rootHandle, token)` with a monotonically-checked token so a stale resume (root re-rendered meanwhile) is a no-op — upstream gets this via closure identity; we must get it via token compare.

### 4.2 Reentrancy contract — entry points, bridge frames, stack budget

**Entry points into the engine (complete list; each is a wasm export or a glue chokepoint):**

| # | Entry | Upstream anchor | Reentrant from |
|---|---|---|---|
| E1 | root create/render/unmount | `ReactFiberReconciler.js` `updateContainer` | app code, effects (nested roots) |
| E2 | update dispatch (`setState`/`dispatch`/`forceUpdate`/context) | `ReactFiberHooks.js:3614`, `ReactFiberClassUpdateQueue.js` | anywhere, incl. mid-commit (S5), mid-render (render-phase updates) |
| E3 | scheduler tick | callback passed to `Scheduler.unstable_scheduleCallback` via S13 chokepoint | scheduler/mock flush |
| E4 | microtask root-processing | `ReactFiberRootScheduler.js:259` | microtask queue |
| E5 | event dispatch → priority + batching | `ReactDOMEventListener.js:121/139/157` → `batchedUpdates` (`ReactDOMUpdateBatching.js:46`) | native events; discrete events sync-flush at batch end |
| E6 | `flushSync` / `flushSyncWork` | `ReactDOMFlushSync.js:19`, `ReactFiberWorkLoop.js:1934` | app code, effects (S6/S7) |
| E7 | Fizz request create / pull / abort | `ReactFizzServer.js:6353/5484` | stream machinery, possibly inside E1-E6 (S19) |
| E8 | act-queue drain | S13 chokepoint + `internalAct.js` flush loops | tests only |

**Bridge-frame stack.** Every export entry pushes a frame `{entryKind, executionContextSnapshot, engineEpoch, jsDepth}` onto an engine-side stack (cap: 64; exceeding it is an engine-poisoning bug — upstream's own reentrancy never exceeds single digits).
- On **normal exit**, the frame pops and asserts the epoch (detects a forgotten nested mutation of engine mode).
- On **user-code throw** (reified, D4): the engine unwinds *its own* state machine for that entry (fiber unwind, Fizz task abort) and returns a tagged error to the *outermost* glue frame of that entry; JS `finally` blocks in glue restore shared-internals slots exactly where upstream does (`ReactDOMFlushSync.js:33-48` pattern: `ReactSharedInternals.T`, update priority).
- On **engine panic/trap**: instance poisoned (D6); every subsequent export returns `POISONED`; glue throws `FerricInternalError` and (in tests) fails loudly.
- Frames at depth >1 are legal only for the pairs the scenarios establish: E2 inside anything; E9 inside anything; E6 inside E12/E5/E3 (flush) and inside E1-render (warn+skip, S6); E1 inside E12/E3 (nested roots); E7 inside anything (S19). All other nestings assert in DEV — matching upstream, which structurally cannot express them.

**Stack budget (verified, F6):** the fiber render loop is iterative (`workLoopSync` `ReactFiberWorkLoop.js:2758`; `workLoopConcurrent`/`ByScheduler` `:3042/:3059`) — bridge nesting is O(#frames), single digits. The recursion hot spots are the commit walks (`ReactFiberCommitWork.js:2016`) and Fizz (`ReactFizzServer.js:4244→3407→3437→3881→4244`), both of which the port makes iterative (D3), because the oracle runs on default ~1 MB stacks under React's own jest configs and Rust frames are 2-5× JS frames. Review rule: **no engine function may recurse on tree/element/child-set depth** — clippy lint + adversarial-review checklist item; the differential fuzz corpus includes 50k-deep chains as a standing regression probe.

### 4.3 Jest/WASM harness spec (lift into the campaign spec's Oracle section)

1. **Artifact shape:** every mapped entry point (`config.build.js:44-50` maps `^pkg$` and `^pkg/entry$` per package directory) is a CJS glue file. Glue evaluation: (a) obtain the compiled `WebAssembly.Module` from the per-realm file-scope cache (compile synchronously on miss — `new WebAssembly.Module(bytes)`; measured 1.8-5.1 ms synthetic, budget ≤30 ms real); (b) rendezvous on the registry-local engine: the first Ferric glue module evaluated in a registry creates `new WebAssembly.Instance` (measured 38-135 µs) and all sibling glue modules share it via an internal `@ferric/engine-rendezvous` module (which, being inside the registry, resets with it). Fresh registry ⇒ fresh instance ⇒ fresh engine state, ~16,000×/run, total added cost seconds, not minutes (F5).
2. **Never** cache engine *instances* outside the registry; **optionally** cache compiled Modules on `process.__ferricModuleCache` (host object shared across jest sandboxes) — M0 must verify cross-realm Module instantiation works in jest's vm contexts before enabling; per-realm caching is the always-safe default.
3. **Scheduling seam** (F3/D2): engine → glue chokepoint → ambient `require('scheduler')`. The chokepoint also implements act-queue diversion (S13). The Rust mock artifact ships the full export surface in F4 with exact yield semantics (`unstable_flushNumberOfYields` stops *between* yields; `waitFor` loops microtasks between flushes — `ReactInternalTestUtils.js:43-90`).
4. **Timers** (F2): glue never calls `setTimeout`/`setInterval`/global `MessageChannel` for engine-driven scheduling. The only timer-ish escapes permitted are the ones upstream artifacts themselves contain (scheduler host config), because tests are calibrated to them (including `patchMessageChannel.js` swapping MessageChannel to fake-timer-setTimeout in 20+ Fizz/Flight tests).
5. **PROD errors** (F8): all engine-originated throws constructed in-sandbox via ambient `Error` with upstream's coded-URL format; codes must exist in `scripts/error-codes/codes.json`; the extraction script runs against `warnings.rs` in CI and fails closed on unknown messages.
6. **Flag parity** (F11): the flag codegen reads `packages/shared/ReactFeatureFlags.js` (the identical file `ReactFeatureFlags.readonly` re-exports) at the pinned SHA; CI diffs generated tables per channel and fails on drift.
7. **Hang policy** (F10): DEV engine fuel guard (~10⁷ units) throws `FerricInternalError('engine fuel exhausted')`; the conformance runner wraps jest and attributes any SIGKILL'd worker to its in-flight test file in the ratchet's infra-red (retry) bucket, never the failure bucket.
8. **M0 harness canaries** (run before any port): (a) `WebAssembly` availability + sync compile/instantiate inside `ReactJSDOMEnvironment`; (b) real-artifact per-reset cost measured across `ReactDOMFizzServer-test.js` (worst offender, 168 cases); (c) `process`-cached Module cross-realm instantiation; (d) RSS trend over a full build-mode run with `--logHeapUsage`. Numbers go in the baseline manifest.

## Cross-lane flags

- **Workflow lane:** the M4 merge-queue unit rows must be cohort rows, not module rows (F7). A module-row backfill queue would deadlock on SCC12 immediately.
- **Packaging lane (judge item 3, CSP):** D1's sync `new WebAssembly.Module` is Node/jest-only; browser packaging keeps streaming instantiation — no conflict, but the glue must carry both loaders behind one entry, and `wasm-unsafe-eval` applies to the browser path only.
