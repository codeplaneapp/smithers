# Serverless Deployment

`smithers cron start` runs a long-lived scheduler process (`apps/cli/src/scheduler.js`) that polls the database every 15 seconds and spawns detached subprocesses for due workflow runs. That model needs a process that stays up. On a serverless platform like Vercel, you instead want a short-lived HTTP handler that a **Vercel Cron** job hits on a schedule.

`runServerlessTick(db, opts)`, exported from `smithers-orchestrator/server`, is exactly that short-lived unit of work: it runs `runCronTick` (claim due crons, start their workflow runs, record the next run time) and then `runResumeTick` (claim and resume runs suspended while detached — see below) and returns a summary of both. Both halves are the SAME functions the CLI uses internally (`runCronTick` backs the scheduler's poll loop, `runResumeTick`'s claim/resume primitive backs `smithers supervise`), so there is one implementation of each behavior for both deployment models.

## Vercel Cron -> route handler -> runServerlessTick

1. Add a [Vercel Cron Job](https://vercel.com/docs/cron-jobs) in `vercel.json` that hits a route on a schedule:

```json
{
  "crons": [
    { "path": "/api/cron-tick", "schedule": "*/1 * * * *" }
  ]
}
```

2. Implement the route handler. It opens the database, calls `runServerlessTick`, and returns the summary:

```ts
// app/api/cron-tick/route.ts (Next.js App Router)
import { SmithersDb } from "@smithers-orchestrator/db/adapter";
import { runServerlessTick } from "@smithers-orchestrator/server";

export async function GET(request: Request) {
  // Vercel signs cron requests with a bearer token; verify it before doing any work.
  const authHeader = request.headers.get("authorization");
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("Unauthorized", { status: 401 });
  }

  const db = await openProductionDb(); // your Postgres/SQLite connection, wrapped in SmithersDb
  const result = await runServerlessTick(db, {
    workerId: `vercel-cron:${process.env.VERCEL_DEPLOYMENT_ID ?? "local"}`,
    // Detached child processes don't outlive a serverless invocation, so
    // provide a startWorkflowRun/resumeRun that fit your deployment (kick off
    // a Vercel Sandbox run, enqueue a job, call an internal API, etc.) — the
    // long agent work always happens in the sandbox/queue/worker, never in
    // this route handler, so the invocation itself stays short regardless of
    // how long the workflow takes to finish.
    startWorkflowRun: async (job) => {
      await startWorkflowRunOnVercelSandbox(job);
    },
    resumeRun: async (job) => {
      await resumeWorkflowRunOnVercelSandbox(job);
    },
  });

  return Response.json(result); // { cron: {...}, resume: {...} }
}
```

3. Set `CRON_SECRET` in your Vercel project environment variables (Vercel automatically sends it as a bearer token to cron-triggered requests).

## Concurrency safety

Vercel Cron does not guarantee exactly-once delivery, and manual triggers or overlapping deploys can call the route concurrently. `runCronTick` claims due crons through `adapter.claimDueCrons(nowMs, leaseMs, workerId)`, an atomic `UPDATE ... WHERE ... RETURNING` claim (implemented once, through the adapter, for both the SQLite and PostgreSQL dialects — see `packages/db/src/adapter.js` and the `_smithers_cron` table's `claimed_at_ms`/`claimed_by` lease columns). Two overlapping `runCronTick` calls cannot both claim (and therefore cannot both fire) the same due cron; a claim that isn't released (e.g. a crashed worker) expires after `leaseMs` (default 5 minutes) and can then be claimed by a later tick.

## The "row not a process" model

Moving cron *firing* to a stateless HTTP handler is straightforward — the cron schedule and lease live entirely in the database row, not in an in-memory timer or long-lived process, so any short-lived process (a serverless function, a fresh CLI invocation) can advance it correctly.

**Advancing a suspended workflow run** (a run paused on a `HumanTask`/approval, or one whose driver process died mid-run) needs the same treatment, and it turns out the engine already supports it: `smithers up <path> --resume --run-id <id>` from a fresh process correctly rehydrates a run from its durable frame/snapshot state (`_smithers_frames`, `_smithers_snapshots` in `packages/db`) and continues it. What was missing wasn't the ability to resume — it was something to *notice* a resumable run and trigger that resume, the run-level equivalent of `runCronTick` noticing a due cron.

`runResumeTick` (see above) is that missing piece: it finds runs resumable because they're `running` but stale (no heartbeat for `staleThresholdMs`, 30s by default — the same threshold `smithers supervise` uses via `--supervise-stale-threshold`), or suspended `waiting-event` with a decided approval or answered human request and no engine alive to act on it (the `approval-decided-resume-required` blocked kind). It claims each through the run-level lease (`db.claimResumableRuns`/`db.releaseRunClaim`, an atomic `UPDATE ... RETURNING` on `_smithers_runs` using the same `claimed_at_ms`/`claimed_by` column names as cron leases) and resumes it. `smithers supervise` delegates its claim/resume handoff to the same lease-backed primitive, so there is one implementation of "claim a resumable run and resume it" for both the long-running CLI supervisor and a serverless tick.

`packages/server` exposes `resumeRun` as an injectable callback because the server package cannot statically import the CLI app that implements `smithers up --resume` without violating the repo's dependency boundaries. The default fallback shells out to the `smithers` binary, which is useful locally, but a Vercel route should pass a `resumeRun` that starts work in a Vercel Sandbox, queue, or worker that outlives the HTTP invocation.

As with `runCronTick`'s `startWorkflowRun`, the long agent work should happen *inside* whatever `resumeRun`/`startWorkflowRun` kicks off (a Vercel Sandbox, a queue consumed by a long-lived worker) — not inside the route handler itself — so the serverless function invocation stays short (just claim + kick off) regardless of how long the resumed workflow takes to finish.
