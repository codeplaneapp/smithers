**Prerequisites:** `bun` installed, and a project directory to run Smithers in.

<Note>
  This cheatsheet is for the agent operating Smithers: run every command
  yourself, never hand it to the human, who only states outcomes and answers
  questions.
</Note>

**Set up**

```bash
bunx smthrs init                                       # scaffold .smithers/
bunx smthrs init --template idea-to-tickets            # return a create-workflow starter request
bunx smthrs starters                                   # browse template IDs
```

**Verify the setup**

```bash
bunx smthrs --version          # prints the version you installed
bunx smthrs workflow doctor    # vcs + workflow pack health
bunx smthrs workflow list      # workflows discovered in this repo
```

`workflow doctor` confirms a VCS resolved and the pack scaffolded (output trimmed):

```text
vcs:
  jj:
    path: jj
    source: path
  git:
    path: git
    source: path
  ok: true
workflowRoot: /your/repo/.smithers
packs[2]:
  - scope: local
    packDir: /your/repo/.smithers
    preload:
      path: /your/repo/.smithers/preload.ts
      exists: true
    bunfig:
      path: /your/repo/.smithers/bunfig.toml
      exists: true
  - scope: global
    ...
workflows[3]:
  - id: create-workflow
  - id: create-skill
  - id: docs-driven-development
```

`ok: true` under `vcs` means jj or git resolved (if `false`, install one; see [Installation](/installation)). A non-empty `workflows[...]` count means the pack is in place. `workflow list` prints the same entries with full metadata.

**Before your first run**

A workflow hands real work to a coding agent: make sure the agent you chose
during `init` is installed and authenticated (e.g. `codex login` for Codex, or
your chosen agent's model/provider credentials). See
[Set up in your harness](/agents/setup) for agent-specific instructions.

**Run your first workflow**

```bash
bunx smthrs workflow run create-workflow --prompt "…"  # build a new workflow from a plain-English ask
bunx smthrs up workflow.tsx --run-id RUN_ID --resume true   # resume a paused run
```

For an implement- or debug-style workflow, `--interactive` prompts for inputs and drops you into the full-screen TUI monitor (TTY only):

```bash
bunx smthrs up workflow.tsx --interactive              # supply inputs interactively, then watch the run
bunx smthrs workflow run WORKFLOW_ID --interactive     # pick a discovered workflow and its inputs
```

**What success looks like**

`workflow run` and `up` stream the lifecycle event log and exit on a terminal line:

```text
[12:00:01] ▶ Run started
[12:00:01] ↺ Run status: running
[12:00:38] ✓ implement (attempt 1)
[12:00:40] ✓ Run finished
```

`✓ Run finished`: the run completed. `⏸ <node> waiting for approval`: paused for a human decision, relay it, then clear with `approve` and resume. `✗ Run failed: …`: reports the error. The CLI prints the run id and next-command suggestions (`logs`, `inspect`) after launch; pass that id to every command below.

**Observe & control**

```bash
bunx smthrs ps                                         # list runs
bunx smthrs inspect RUN_ID                           # structured run state
bunx smthrs logs RUN_ID --tail 20 --follow           # stream events
bunx smthrs why RUN_ID                               # why is it paused?
bunx smthrs approve RUN_ID --node NODE_ID --by NAME   # approve a paused node
bunx smthrs cancel RUN_ID                            # cancel a run
```
