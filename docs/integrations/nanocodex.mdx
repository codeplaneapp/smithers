`NanocodexAgent` connects Smithers to the external
[`smithers-nanocodex`](https://github.com/N0xMare/smithers-nanocodex)
bridge. The adapter does not bundle or download the executable at runtime.
Install the published v0.0.2 binary for your host, verify it against the
release `.sha256` sidecar, then select it with `binary` or `PATH`.

The v0.0.2 integration is deliberately fixed: one fresh `serve` worker and one
stock Nanocodex turn per `generate()` call. There is no daemon, worker pool, or
bridge-session reuse. `generate()` also performs a short, provider-free
capability check before starting that worker. The worker is spawned directly,
the same class as other Smithers CLI agents. Isolation, if required, is an
outer Smithers `<Sandbox>`. The adapter must not wrap this binary in
Bubblewrap or `sandbox-exec`.

v0.0.1 / Nanocodex 0.3.0 checkpoints do not resume. The tool profile is
`nanocodex-stock-0.5.0`.

## Requirements

- One of the shipped hosts:
  - Linux x64 (`x86_64-unknown-linux-gnu`), glibc 2.35 or newer; Ubuntu 22.04
    is the oldest supported baseline
  - macOS arm64 (`aarch64-apple-darwin`)
- Smithers on Node.js 22 or Bun 1.3 or newer
- The matching `smithers-nanocodex` v0.0.2 binary on `PATH` or selected with
  `binary`

Windows, Linux arm64, Intel macOS, musl, and older glibc versions fail before
the bridge starts. Bubblewrap is not required and must not wrap the worker.

## Install the published v0.0.2 binary

The adapter does not download the executable. Install the published
[`v0.0.2`](https://github.com/N0xMare/smithers-nanocodex/releases/tag/v0.0.2)
archive for your host and verify it against the release's `.sha256` sidecar
before putting the binary on `PATH`. Smithers does not duplicate those sidecars
as an in-repo pin digest.

| Host         | rustc target               | Archive                                                     |
| ------------ | -------------------------- | ----------------------------------------------------------- |
| Linux x86_64 | `x86_64-unknown-linux-gnu` | `smithers-nanocodex-v0.0.2-x86_64-unknown-linux-gnu.tar.gz` |
| macOS arm64  | `aarch64-apple-darwin`     | `smithers-nanocodex-v0.0.2-aarch64-apple-darwin.tar.gz`     |

```bash
# Linux x86_64. On macOS arm64 use target=aarch64-apple-darwin and `shasum -a 256 -c`.
tag=v0.0.2
target=x86_64-unknown-linux-gnu
package="smithers-nanocodex-${tag#v}-${target}"
base="https://github.com/N0xMare/smithers-nanocodex/releases/download/${tag}"

curl -fsSL -O "${base}/${package}.tar.gz"
curl -fsSL -O "${base}/${package}.tar.gz.sha256"
sha256sum -c "${package}.tar.gz.sha256"
tar -xzf "${package}.tar.gz"
sudo install -m 0755 "${package}/smithers-nanocodex" /usr/local/bin/smithers-nanocodex
```

The historical `packages/agents/tests/fixtures/nanocodex/source-build-v0.0.1.json`
record is the immutable v0.0.1 source-build pin. It is not the current adapter
contract. The prepared v0.0.2 consumer contract lives at
`packages/agents/tests/fixtures/nanocodex/release-v0.0.2.json` and does not
embed published sidecar digests.

## Configure the adapter

With the executable on `PATH`, no binary option is needed:

```tsx
import { NanocodexAgent } from "smthrs";

const agent = new NanocodexAgent({
  cwd: "/absolute/path/to/workspace",
  model: "gpt-5.6-sol",
  thinking: "high",
  reasoningMode: "standard",
});
```

Set `binary` to an executable name resolved through `PATH` or to a path. The
adapter resolves and canonicalizes the executable during preflight.

```tsx
const agent = new NanocodexAgent({
  binary: "/opt/smithers/bin/smithers-nanocodex",
  cwd: "/srv/workspaces/project",
  inheritEnv: false,
  env: {
    PATH: "/usr/local/bin:/usr/bin:/bin",
    NANOCODEX_OPENAI_KEY: process.env.NANOCODEX_OPENAI_KEY!,
  },
  auth: {
    mode: "api-key-env",
    environmentVariable: "NANOCODEX_OPENAI_KEY",
  },
});
```

When `inheritEnv` is `false`, ambient process variables are not inherited. The
`serve` worker receives variables configured in `env` plus any Smithers
task-context identifiers supplied for the call: `SMITHERS_RUN_ID`,
`SMITHERS_NODE_ID`, `SMITHERS_ITERATION`, `SMITHERS_ATTEMPT`, and
`SMITHERS_INSIDE_RUN` (the recursion marker that tells the worker it is already
running inside a node and must not launch or steer another run). Include `PATH`
in `env` if `binary` is a command name; ambient `PATH` is not used in this mode.
Prompts, credentials, and snapshots never appear in process arguments.

## Authentication

API-key mode is the default and reads `OPENAI_API_KEY`. You can name another
bridge-process environment variable as shown above. The credential value stays
out of protocol JSON, although same-UID host processes may still inspect the
bridge environment through facilities such as Linux `/proc`.

Managed ChatGPT mode uses the normal Nanocodex/Codex auth file or an explicit
absolute path:

```tsx
const agent = new NanocodexAgent({
  auth: {
    mode: "chatgpt",
    authFile: "/home/worker/.codex/auth.json",
  },
});
```

Within one Smithers JavaScript process, managed-ChatGPT `generate()` calls that
resolve to the same canonical auth file are FIFO-serialized across
`NanocodexAgent` instances. The gate covers the `serve` worker through verified
process closure; provider-free preflight may still run concurrently, and the
gate releases before checkpoint publication. Calls using different auth files
and all API-key calls remain concurrent. A queued caller may abort promptly,
but later waiters do not overtake the active call.

This serialization is process-local. Do not run another Smithers process,
Nanocodex bridge, or other credential-refreshing process against the same auth
file concurrently.

`preflight()` checks the host, executable, and declared target/version/capability
surface without loading credentials or contacting a provider.
The actual managed-ChatGPT adapter suite is
`packages/agents/tests/nanocodex-live.test.js`. It is opt-in/manual through
`SMITHERS_RUN_NANOCODEX_LIVE=1`, not part of normal package-test execution, and
must run only in a trusted environment. The engine cold-restart suite at
`packages/engine/tests/nanocodex-live-workflow.test.js` uses the same opt-in
gate. Never enable either suite in a fork pull request or any job that exposes
repository secrets.

## Fixed v0.0.2 surface

| Capability                               | v0.0.2 behavior                                                                                                                                                                                                  |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model                                    | Allowlisted `gpt-5.6-sol` (default), `gpt-5.6-terra`, `gpt-5.6-luna`; aliases `sol` / `terra` / `luna`. Fixed per native thread; resume rejects a mismatched constructor model (absent checkpoint model is Sol). |
| Native tools and Code Mode               | Enabled                                                                                                                                                                                                          |
| Transport                                | WebSocket preferred, with stock sticky HTTPS fallback                                                                                                                                                            |
| Checkpoints                              | `nanocodex.session-snapshot/1`, resume only                                                                                                                                                                      |
| Structured output                        | Prompt-based Smithers extraction, not native schema output                                                                                                                                                       |
| JavaScript tools and MCP                 | Unsupported                                                                                                                                                                                                      |
| Subagents and steering                   | Unsupported                                                                                                                                                                                                      |
| Custom provider endpoints                | Unsupported                                                                                                                                                                                                      |
| Code Mode disablement                    | Unsupported                                                                                                                                                                                                      |
| Workspace relocation and checkpoint fork | Unsupported                                                                                                                                                                                                      |

`instructions` replaces the stock instructions completely. Per-call system
messages, JavaScript tools, provider options, and `resumeSession` are rejected.

## Checkpoints and workspace identity

Each completed turn returns a durable Smithers checkpoint containing the exact
opaque Nanocodex snapshot. Resume is accepted only when the checkpoint's
`canonicalWorkspace` exactly matches the current canonical workspace, along
with the bridge, Nanocodex, snapshot, codec, and policy versions. Moving a
checkpoint across worktrees, machines, symlink-resolved roots, or absolute
workspace paths is unsupported. Fork mode is unsupported.

Treat checkpoints as secrets. A snapshot may contain conversation context,
tool results, source material, paths, or credentials that the agent read.
Smithers validates and bounds the envelope but does not sanitize the opaque
snapshot.

## Process cleanup is not isolation

The adapter spawns `smithers-nanocodex` directly. Linux `detached` process-group
signaling and guarded `/proc` tracking are supplemental best-effort cleanup, not
a launch gate and not PID-namespace-authoritative. They are **not** filesystem,
network, device, or credential isolation. Use an outer Smithers `<Sandbox>`
when your deployment needs those boundaries.

## Qualify a local archive

From a Smithers checkout on a supported host, this command inspects a local
v0.0.2 archive and runs the public adapter preflight:

```bash
node scripts/qualify-nanocodex-release.mjs \
  --archive /absolute/path/to/smithers-nanocodex-v0.0.2-x86_64-unknown-linux-gnu.tar.gz
```

`--archive` is required. The command reads no remote source, rejects the input
unless it is a non-empty regular file no larger than 8 MiB, computes its
SHA-256, and safely inspects its layout. Current v0.0.2 archives are reported
as `unverified-input` because Smithers does not embed the published sidecar
digests. The historical v0.0.1 source-build digest remains loadable as an
immutable record and is not the current runtime contract.

A direct local invocation does not itself initiate a network request, but the
probed executable has ordinary host networking. Add an external network
boundary when running an untrusted local input.

In a temporary scratch workspace, the verifier materializes the archive
executable. It runs exact-version and full-capability probes through the same
direct-spawn supervisor used by the adapter, then invokes public
`NanocodexAgent.preflight()` against the same path with `inheritEnv: false`
and an empty environment. Neither probe performs a model turn or needs a
provider credential. Scratch state is removed on success or failure.
