# Migrating from Smithers 0.x

This guide is for an operator with a working Smithers 0.x project: JSX workflows, `createSmithers`, `<Task>`, a `.smithers` pack. It covers what changes, the three commands, how to read the report, and what to do with what the tool refuses.

The tool is `@smthrs/migrate`. Its API reference is [migrate](/migration/migrate-tool), and the agent-facing version is `skills/migrate-smithers-v1/SKILL.md`.

## What changes

Smithers 1.0 has no JSX authoring stack, no React reconciler, and no old engine. A workflow is a `Flow`, a step is an `Action`, control flow is `Node.andThen`, `Node.all`, and `Node.branch`, and a model-backed step is an `AgentAction`. Schemas are `effect/Schema` rather than zod.

| Old | New |
| --- | --- |
| `createSmithers` + `<Workflow>` | `Flow.make(tag, { payload, success, error, body })` in `flows/<name>/flow.ts` |
| `<Task>` with a closure | `Action.make(tag, { payload, success })` and `.toLayer(handler)` |
| `<Task agent>` with prompt children | `AgentAction.make(tag, { payload, output, seat, system, prompt })` |
| `<Sequence>` / `<Parallel>` / `<Branch>` | `Node.andThen` / `Node.all` / `Node.branch` |
| `<Timer>` / `<WaitForEvent>` / `<Approval>` | `Sleep.action` / `WaitFor.action` / `WithApproval.withApproval` |
| `<Loop>` / `<Ralph>` / `<ReviewLoop>` | `ReviewLoop.run`, or `Recursion.recurse` with explicit fuel |
| `deps`, `ctx.output`, `outputs.x` | The planned value the previous node returned |
| An agent adapter or a pool | A seat string a `SeatResolver` resolves |

The migration tool rewrites your source to that model. It is not a compatibility layer: nothing it writes recreates the JSX runtime, embeds a scheduler in application code, or hides a construct it could not translate behind `any`.

## Before you start

Node 22.19 or newer, a jj or git checkout, and a model key: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or `OPENROUTER_API_KEY`.

Uncommitted work survives. The checkpoint opens a jj change or writes a git ref and never touches the working tree, and a failed unit is restored only for the files that unit claimed. Commit first anyway: a diff you can read beats one you have to reconstruct.

## Three commands

```sh
npx @smthrs/migrate                       # plan
```

Reads the project and writes `.smithers-migrate/report.md` and `report.json`. It changes nothing else. Read that report before you go further; it is the whole decision.

```sh
npx @smthrs/migrate --apply --seat anthropic:<model>
```

Migrates one unit at a time: dependencies first, then one unit per workflow file in dependency order, then integrations, then the project itself. Each unit checkpoints, rewrites, and verifies with your own commands.

```sh
npx @smthrs/migrate --apply --unit workflow:release --seat anthropic:<model>
```

Reruns part of a plan after you have changed something it depends on.

The seat is a `provider:model` pair. The tool has no default model and never picks one: a default would be a choice about your money.

## Two refusals

`--apply` exits 3 without touching the project in two cases.

**The project still holds 0.x run state.** A `smithers.db`, a `.smithers/executions/` directory, a `SMITHERS_BACKEND` or Postgres setting. A 1.0 runtime cannot read any of it, and the tool will not rewrite or resume it. Finish the live runs, cancel or archive the parked ones, then move or delete the database. The report lists exactly what it found and what to do, in order. When you have decided, pass `--acknowledge-run-state`. The data is still never touched: the kernel denies every write the agent makes under those paths, refuses every shell command that is not one of the project's own verification commands, and each unit checks a digest of every run-state file afterwards and restores itself if a byte moved.

**Something has no safe translation.** A workflow UI, a worktree, `continueAsNew`, a direct store read, a Postgres backend, an integration package. Each one is named with the closest 1.0 composition there is. Decide what happens to each, then pass `--allow-unsafe <name,...>`, or `--allow-unsafe all`, and the tool leaves a `TODO(migrate-smithers-v1): <construct>` marker where each one was, plus a report entry, rather than an imitation.

## Verification

Every unit runs your project's own commands: install by lockfile, `dprint fmt` or `prettier --write` if you have one configured, `tsc --noEmit` per covering tsconfig, your `test` script, and flow discovery over `flows/`.

Override any of them with `--verify-install`, `--verify-format`, `--verify-typecheck` (pass it once per command), and `--verify-test`. Read the plan's report first: it names the commands the tool derived, and a wrong one is worth correcting before you apply. Every unit is verified with these lines and the agent's own shell is allowed exactly them, so a project whose typecheck lives in a Makefile needs the override to be migrated at all. `--verify-typecheck ""` runs no typecheck.

A unit that fails is handed back to the agent with the failing output, up to `--max-repair-rounds` times (three by default). After that its checkpoint is restored, the unit is recorded as `failed`, and the next unit runs. The run does not stop.

## Reading the report

`report.md` sections, in order: summary, run state and instructions, project detection, construct inventory, mapping decisions, one section per unit, final verification, manual follow-ups, and the commands that restore each checkpoint. The Markdown is deterministic for a given JSON, so two runs diff cleanly.

Exit codes: `0` every planned unit finished, `1` a unit failed and was restored, `3` a gate refused and the project is untouched.

Work the follow-up list top down. `must` items block; `should` items are the ones a person has to answer, and every agent pool is one of them. A `fallbackAgents` chain is an operator decision, and the tool preserves it as a pool rather than choosing a seat for you.

Commit `report.md`. It is the record of what changed, what could not be translated, and what is left.

## Undoing it

Each unit's report section carries the command that restores its checkpoint: `jj restore --from <change>`, `git checkout <ref> -- .`, or a copy back from `.smithers-migrate/backup/<unit>/`. The sources the migration replaced are in `.smithers-migrate/archive/` under their original paths unless you passed `--keep-old-sources`; a unit that failed leaves nothing there, because whatever put it back took its archive copies with it. Your `package.json`, `tsconfig*.json`, and `.gitignore` are never moved there: they are rewritten where they are, so the diff you review is a diff.

## What a unit may touch

A unit may write only the files the plan gave it. Before it starts, the tool digests every file in the project except `.git`, `.jj`, `node_modules`, the report directory, `.flows/`, and the 0.x run-state paths, which have a stricter check of their own. Afterwards it compares. That comparison, not the agent's account of itself, is what the report's changed-file list is built from.

A write outside the unit's file set fails the unit. A file it added is removed. A file it modified is left where it is and named in the report with the command that restores the checkpoint, because the checkpoint copied the unit's own files aside and nothing else — the tool will not delete work it never backed up.
