Smithers is mostly built for your agent, not for you: your agent reads the
[Technical API](/introduction) and does the operating. But knowing what
Smithers *can* do helps you put its most powerful features to work, and that
is what this page is for.

[What You Can Do](/guide/what-you-can-do) catalogs the workflows Smithers runs.
This page catalogs everything *around* those runs: the platform capabilities a
run picks up for free. You don't operate any of this by hand; you ask your
agent, exactly as in [Talk to Your Agent](/guide/talk-to-your-agent), and it
runs the command or writes the config shown. Each row pairs what you say with
what Smithers does under the hood. The deeper links lead into the Technical
API; point your agent at them instead of reading them yourself. The few
genuinely human steps (connecting your harness, signing up for semantic
memory) live in the Set up pages, starting at
[Set Up with Claude Code](/guide/setup/claude-code).

## Plug in your own logging

Smithers logging is structured and replaceable, whether you run the CLI or
embed Smithers in your own server.

| You say | Smithers runs under the hood |
| --- | --- |
| "Ship Smithers logs into our logging stack as JSON, warnings and up." | `SMITHERS_LOG_FORMAT=json` + `SMITHERS_LOG_LEVEL=warn`; formats are `logfmt`, `json`, `pretty`, `string`. |
| "We embed Smithers in Node and already have a logger. Use ours, not yours." | `createExternalSmithersEngine({ logger })` scopes structured engine logs to the host-owned sink ([Embed the engine in Node](/integrations/embedded-engine)). Lower-level Effect hosts can use `createSmithersObservabilityLayer({ installLogger: false })`. |
| "Mirror every run event and failure into our own sink." | The `onProgress` and `onError` run callbacks, which receive every event and failure report as plain objects. |
| "Send traces and metrics to our Grafana / Datadog." | OTLP export via `SMITHERS_OTEL_ENABLED=1` + `OTEL_EXPORTER_OTLP_ENDPOINT`; Prometheus text at the server's `GET /metrics`. |
| "Give me a local dashboard with traces so I can poke around." | `bunx smthrs observability`: a Grafana + Prometheus + Tempo + OTLP collector stack via Docker Compose. |

## Get alerted

| You say | Smithers runs under the hood |
| --- | --- |
| "When the nightly release run fails, page the on-call with the runbook link." | An `alertPolicy` on the workflow (ownership, severity, runbook, reactions), with durable alert rows via `bunx smthrs alerts` ([Alerting](/guides/alerting)). |
| "Send me a daily digest of my runs on Telegram." | The [Telegram integration](/integrations/telegram) and the `telegram-daily-digest` pack workflow. |

## Go back in time

Every step of every run is checkpointed, so history is something you can act
on, not just read.

| You say | Smithers runs under the hood |
| --- | --- |
| "That refactor went sideways at step 4. Rewind to just before it." | `bunx smthrs rewind` back to the good frame. |
| "Fork the run from before the review step and try a different approach." | `bunx smthrs fork`, then `replay` drives the branch forward. |
| "Show me every checkpoint this run took and what each one changed." | `bunx smthrs timeline`, `snapshots`, and `diff`. |
| "Put my files back the way they were before that task ran." | `bunx smthrs restore` / `revert` reset the working tree to a checkpoint. |

See [time travel in Recipes](/recipes#time-travel-fork-replay-diff) for the full loop.

## Stop failing runs from spinning

A step that keeps failing the same way is not making progress, and Smithers
stops it instead of burning the retry budget.

| You say | Smithers runs under the hood |
| --- | --- |
| "That step failed the same way 80 times. Stop it after a few and tell me." | Non-progress detection: after 3 consecutive attempts with an identical error signature the node goes to the `stalled` state; tune it with `retryPolicy={{ maxIdenticalFailures: N }}` ([Retries and Recovery](/capabilities/retries-and-recovery)). |
| "Never retry this gate. If it fails, it failed." | `retryPolicy={{ retryable: false }}`, or a `retryable(error)` predicate to veto only some failures. |
| "The run error just says the node name. Tell me what actually broke." | Run-level errors carry the failing node, the attempt count, and the last attempt's real error payload. |
| "It failed. What do I run to pick up where it left off?" | The failure output and `bunx smthrs why` print the last good checkpoint with the exact `up --resume` and `replay --frame` commands. |

## Take over mid-run

| You say | Smithers runs under the hood |
| --- | --- |
| "Hand me that agent session; I'll drive it from my terminal." | `bunx smthrs hijack` hands the run's live agent session to you, resumable. |
| "Pause the migration run: finish what's in flight, start nothing new." | `bunx smthrs pause` parks it durably; resume later with `up --resume RUN_ID`. |
| "The run is waiting on the deploy; tell it the deploy finished." | `bunx smthrs signal` delivers the event a waiting run is listening for. |
| "Did any run ask me a question? Show me, and let me answer." | `bunx smthrs human` lists and resolves durable questions raised mid-run. |
| "If my overnight runs stall, resume them automatically." | `bunx smthrs supervise` watches named runs and auto-resumes them. |

## Teach it and tune it

| You say | Smithers runs under the hood |
| --- | --- |
| "What has Smithers learned about this repo across runs?" | `bunx smthrs memory`: cross-run memory facts, queryable ([Memory](/concepts/memory)). |
| "Give it memory that recalls by meaning, not keywords." | A Hindsight endpoint via `HINDSIGHT_URL`. Signing up or self-hosting is the one step your agent can't do for you: [Set Up Semantic Memory](/guide/setup/semantic-memory). |
| "Protect this workflow with regression cases we can run in CI." | `bunx smthrs eval` over a JSON/JSONL suite, emitting a check-in-able report ([Eval Suites Quickstart](/guides/evals-quickstart)). |
| "How did the last few runs score?" | `bunx smthrs scores` ([Scorers](/reference/scorers)). |
| "Make the reviewer prompt better, and prove it's better." | `bunx smthrs optimize`: GEPA prompt optimization verified against your eval suite ([Workflow optimization](/guides/workflow-optimization)). |

## Accounts, quota, and cost

| You say | Smithers runs under the hood |
| --- | --- |
| "Use my Claude subscription for the smart steps and my OpenAI key for the rest." | `bunx smthrs agents`: register subscriptions and API keys, then route each task to the right one. |
| "Add my teammate's Claude account as another seat." | `bunx smthrs agents add --provider claude-code --label claude-2 --tmux` runs the browser login in tmux and registers the isolated config dir. |
| "Spread this run across all our Claude and Codex subscriptions so rate limits never stall it." | `fallbackAgents()` puts every registered seat on one shuffled failover chain, normal agent last. |
| "Route around the Fable weekly limit; save Fable-capable seats for Fable work." | `bunx smthrs usage` reports the model-scoped `weekly (Fable)` window, and `fallbackAgents()` orders seats by headroom in the window the rung's own model draws from. |
| "How much of my quota have runs burned this week?" | `bunx smthrs usage` per registered account. |

## Share and extend

| You say | Smithers runs under the hood |
| --- | --- |
| "Install that team's review pack." | `bunx smthrs add` from GitHub, npm, or a local file. |
| "Publish our pack so other teams can install it." | `bunx smthrs share` opens the pull request for you. |
| "Update the packs we've installed." | `bunx smthrs packs update`. |
| "Copy the built-in implement workflow into the repo so we can customize it." | `bunx smthrs eject` copies the workflow plus its UI, prompts, and libraries. |
| "Let this agent call our research workflow like a tool." | `workflowTool({ name, workflow })` derives parameters from the workflow input schema and runs each call as an attributed child run ([Workflow tools](/components/workflow-tool)). |
| "Upgrade Smithers itself." | `bunx smthrs update`, or `upgrade` for the agent-assisted path. |

## Quick jobs, no workflow

| You say | Smithers runs under the hood |
| --- | --- |
| "Fix this bug (or upgrade every dependency, or make CI green) in the background and show me a live dashboard with the diff." | `bunx smthrs oneshot`: one strong agent, one goal at any size, up to roughly 300k tokens in a single run, with chat/diff/hijack controls ([Oneshot](/guides/oneshot)). |
| "Open that oneshot so I can watch it live, steer the agent, or restart it." | `bunx smthrs monitor RUN_ID`: the dedicated oneshot monitor with streaming chat, honest steering delivery, restart, and an attachment-scoped cheap narrator. |
| "Review this PR and give me a walkthrough I can actually read." | `bunx smthrs review`: code review plus a story-form HTML walkthrough. |
| "What happened in that run?" / "Why is it stuck?" | `bunx smthrs what` / `why`: a narrated recap, or the exact blocker. |
| "Ask Smithers how I'd do X." | `bunx smthrs ask` answers from the installed docs and MCP server. |

## Run it your way

| You say | Smithers runs under the hood |
| --- | --- |
| "Run the risky steps in an isolated cloud sandbox." | Sandbox providers: Microsandbox, Daytona, Vercel, AWS, GCP ([Sandbox providers](/components/sandbox-providers)). |
| "Let a teammate watch and approve from their laptop." | `bunx smthrs gateway` serves the HTTP control plane; `token` mints short-lived access ([Gateway](/integrations/gateway)). |
| "Keep run history in our Postgres, not a local SQLite file." | `bunx smthrs migrate` moves the run store to PGlite or Postgres ([Database](/reference/db)). |
