An agent step fails differently than an HTTP call fails. An HTTP call fails loudly and cheaply: a 503, a timeout, a connection reset. Retry it with backoff and jitter and you are mostly done. An LLM step can fail *silently* - a schema violation, a confidently wrong answer, a truncated response at the context-window edge - and it can fail *expensively*: the failed attempt already spent twenty minutes and half a million tokens, and it may already have edited files, pushed a commit, or sent a webhook. Retrying it blindly re-runs those side effects; not retrying it strands a six-hour run at step four of nine.

So classical retry theory is necessary but not sufficient here. You still need bounded attempts, exponential backoff, and error classification - providers do rate-limit and 5xx like everyone else. But you also need things an HTTP retry loop has no concept of: per-attempt *filesystem* state (attempt 2 must not inherit attempt 1's half-finished edits), escalation to a different or stronger model rather than the same one that just failed, a distinction between "the agent failed" and "the provider's quota is exhausted" (the second says nothing about the agent), and explicit side-effect containment for actions that cannot be un-sent.

This page covers the whole failure path in Smithers: what a retry policy looks like on a `<Task>`, how attempts are recorded, how a multi-agent failover chain escalates, what happens on quota exhaustion, and the operator surface - `retry-task`, `revert`, `supervise`, `cancel`, `bug`, and the automatic post-failure autopsy.

## How the industry handles failure

Every serious execution system converges on the same handful of mechanisms:

| System | Mechanism | Tradeoff |
| --- | --- | --- |
| [Temporal](https://docs.temporal.io/encyclopedia/retry-policies) | Per-activity `RetryPolicy`: `initialInterval` (1s), `backoffCoefficient` (2), `maximumAttempts`, `nonRetryableErrorTypes`; `heartbeatTimeout` detects hung workers | Powerful but every knob is your problem; retries assume idempotent activities |
| [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html) | `Retry`/`Catch` arrays matched by `ErrorEquals`, with `IntervalSeconds`, `BackoffRate`, `MaxAttempts`, and a `JitterStrategy` | Declarative and auditable; error taxonomy is string-matching |
| [AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) (Brooker) | Full jitter: `sleep = random(0, min(cap, base·2^n))` - kills synchronized retry storms | Randomness makes individual latency less predictable |
| [Hystrix / resilience4j](https://resilience4j.readme.io/docs/circuitbreaker) | Circuit breaker: CLOSED → OPEN at a `failureRateThreshold`, probe via HALF_OPEN | Fails fast during outages; a mis-tuned breaker rejects healthy traffic |
| [SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html) | After `maxReceiveCount` failed receives, the poison message moves to a DLQ for inspection | Isolates poison work; someone must actually look at the DLQ |
| [Saga pattern](https://microservices.io/patterns/data/saga.html) | Compensating transactions semantically undo committed steps that can't be rolled back | Compensations must themselves be idempotent and retriable |
| [Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) | `restartPolicy` + CrashLoopBackOff: restart delay doubles from 10s, capped at 5m | Simple and universal; knows nothing about *why* the process died |

What none of these cover are the agent-specific failure modes: nondeterministic output (the retry may succeed for no reason, or fail differently), schema-invalid output that is not an "error" at the transport level, context-window exhaustion, and the silent wrong answer that no retry policy can detect - only a scorer or reviewer can. Smithers borrows the classical mechanisms (backoff, heartbeats, compensation, a breaker for dead agents) and adds the agent-shaped ones on top.

## Retry policy on a Task

The retry surface lives directly on `<Task>` (verified in `packages/components/src/components/TaskProps.ts`):

```tsx
<Task
  id="implement"
  agent={[codex, opus]}            // failover chain: tries in order across retries
  retries={3}                       // attempt budget; default is Infinity
  retryPolicy={{ backoff: "exponential", initialDelayMs: 2000 }}
  timeoutMs={10 * 60_000}
  heartbeatTimeoutMs={120_000}      // no output/heartbeat for 2m ⇒ attempt fails
  output={outputs.z.object({ summary: z.string() })}
>
  Implement the feature described in the spec.
</Task>
```

The pieces, as implemented:

- **`retries`** - additional attempts after the first. The default is **infinite retries** with exponential backoff starting at 1s (`resolveRetryConfig` in `packages/graph/src/extract.js` returns `retries: Infinity` and `{ backoff: "exponential", initialDelayMs: 1000 }` when nothing is set). Bound it with `retries={N}` or disable with `noRetry`. `continueOnFail` tasks default to 0 retries - except agent tasks, which get one free retry for transient CLI flakes.
- **`retryPolicy`** - `{ backoff: "fixed" | "linear" | "exponential", initialDelayMs, maxIdenticalFailures, retryable }`. Delays are computed as an Effect `Schedule` and capped at **5 minutes** (`packages/scheduler/src/retryPolicyToSchedule.js`). There is no jitter today; with typical fan-outs of tens of lanes against one provider, that is a real (if modest) gap versus [full jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/). `maxIdenticalFailures` and `retryable` are the non-progress and classification knobs described below.
- **`maxSchemaRetries`** - separate from failure retries: up to 3 (default) cheap correction calls when output doesn't parse against the Zod schema, before the attempt is considered failed at all.
- **`timeoutMs` / `heartbeatTimeoutMs`** - a hard wall-clock limit and a Temporal-style liveness check: an agent that stops producing output past the heartbeat window fails the attempt instead of hanging the run.
- **`continueOnFail` / `failurePolicy`** - whether a terminal failure halts the run, or quarantines the branch and lets independent work proceed.

### Dead worker detection

Liveness does not depend on declaring `heartbeatTimeoutMs`. When the agent CLI
process the engine spawned for an attempt exits at the OS level (any exit code,
including a signal) while its `generate()` call is still outstanding, the engine
fails that attempt with `AGENT_WORKER_EXITED` once a short grace period passes
with no result. This catches the case where a worker is killed but a leaked
grandchild (an MCP server, a tool child) keeps the capture pipe open, so the
adapter promise never settles and the lane would otherwise sit `in-progress`
forever. The failure is an ordinary retryable attempt failure: `retries`,
`retryPolicy`, and the `agent` failover chain all apply. Detection is armed only
after a worker start is observed and is disarmed the moment another worker
starts, so a healthy but slow attempt and a resumed session that reattaches to
an existing worker are never affected.

### Non-progress detection: the `stalled` state

A task that fails 84 times with a byte-identical error is not retrying, it is livelocked. Smithers computes a stable **error signature** for every failed attempt (the error code plus its message with paths, ids, and numbers normalized away, `packages/scheduler/src/errorSignature.js`) and counts consecutive failures that share it. After `maxIdenticalFailures` of them (default **3**) the task stops retrying and enters a terminal state of its own: **`stalled`**, distinct from `failed`.

```tsx
<Task
  id="author-diagram"
  agent={author}
  retries={20}
  retryPolicy={{ maxIdenticalFailures: 3 }}   // default; 0 disables stall detection
  output={outputs.diagram}
>
  Draw the sequence diagram.
</Task>
```

What `stalled` gives you over `failed`:

- The streak is recomputed from durable attempt rows on every failure, so the verdict survives a resume or an owner handoff. The count and the signature are stamped on the attempt (`details.identicalFailureStreak`, `details.errorSignature`).
- A `NodeStalled` event carries the signature, the repeat count, and the full error payload.
- `bunx smthrs status`, `bunx smthrs inspect`, `bunx smthrs why`, the TUI, and the run UIs render `stalled` as its own status, so a livelock does not read as an ordinary failure.
- The run-level error is a `TASK_STALLED` SmithersError naming the node, the repeat count, and the real message.

`stalled` behaves exactly like `failed` for control flow: `continueOnFail` still tolerates it, `failurePolicy="quarantine"` still quarantines the branch, and dependents are still gated. Two failure classes never stall: quota failures, which park the run instead of consuming any budget, and transient agent-session failures (`SESSION_ERROR`, `TASK_TIMEOUT`, `TASK_ABORTED`), which the run already tolerates rather than failing on.

### Failure classification: what is never retried

Some failure shapes cannot be fixed by running the task again, so Smithers classifies them **before** scheduling a retry and sends them straight to the terminal state with the full payload (`packages/scheduler/src/failureClassification.js`):

| Shape | Why retrying is waste |
| --- | --- |
| `ENOENT` in the error message | A missing filesystem precondition. `statx` on a path that does not exist fails the same way on attempt 74. |
| Any `*_TOO_LARGE` error code | A hard size cap (heartbeat payload, tool file or patch, sandbox bundle). Regenerating the same artifact breaches the same cap. |
| `AGENT_CONFIG_INVALID` | The agent is misconfigured, not flaky. |
| `INVALID_OUTPUT` on a non-agent task | A compute or static task is deterministic, so the schema violation reproduces. |

Agent-task schema violations are deliberately **not** on that list: a fresh generation may well parse. Those are caught by stall detection once the failures start repeating byte-identically.

For anything the platform cannot classify, declare it yourself with `retryPolicy.retryable`:

```tsx
<Task
  id="verify-contract"
  agent={verifier}
  retryPolicy={{ retryable: (error) => error?.code !== "CONTRACT_VIOLATION" }}
>
  Verify the generation-input boundary.
</Task>

<Task id="gate" retryPolicy={{ retryable: false }} agent={gate}>Check the invariant.</Task>
```

`retryable: false` makes every failure of the task terminal. A `retryable(error)` predicate is consulted per failure; returning `false` makes that failure terminal while other failures keep their retry budget. A predicate that throws is treated as an authoring bug and the failure stays retryable, so a bad predicate can never wedge scheduling.

### Escalation: the failover chain

`agent={[cheap, strong]}` (or `fallbackAgent={strong}`) is a failover chain. Attempt N runs on rung N−1: the retry doesn't just re-roll the same model, it escalates to the next agent. Two refinements in `packages/engine/src/engine.js` matter:

- **Quota failures don't advance the rung.** A provider quota wall says nothing about the agent's health, so quota-failed attempts are discounted when picking the rung - otherwise one Codex quota blip would silently demote every task onto its fallback for the rest of the run.
- **A run-wide breaker for dead agents.** An agent that fails preflight (e.g. a 401 from a bad API key) is disabled run-wide and selection skips it - a per-agent circuit breaker in the [Hystrix](https://resilience4j.readme.io/docs/circuitbreaker) sense, so a documented fallback actually engages instead of every task dying on the broken rung first.

### Repair after terminal failure

Retries and agent fallbacks repeat the same work. They cannot create a missing
file, repair a drifted generated artifact, or restore another precondition.
Declare `repair` when a separate bounded task should change that state:

```tsx
<Task
  id="publish"
  output={outputs.publication}
  retries={2}
  agent={fallbackAgents({ seed: ctx.runId })}
  repair={{
    agent: repairAgent,
    output: outputs.repair,
    instructions: "Repair only the missing publication inputs.",
  }}
>
  Publish the prepared artifacts.
</Task>
```

The unit is a repair task, not a fallback result. The original retry policy and
agent chain run first. Only a terminal failure triggers repair. After repair
succeeds, Smithers gives the original task one fresh attempt starting at the
first agent in its chain. This keeps `fallbackAgents` responsible for a
different agent doing the same work and keeps `repair` responsible for changing
the precondition.

The repair receives the terminal error, all durable attempt summaries, the
original task's prompt or payload, resolved workflow input and dependency
outputs, and the active workspace path and branch. Each attempt summary includes
timing, state, error, and the jj pointer. Its result is validated and persisted
through the declared Zod output target. It runs in the same workspace as the
failed task.

Repair is bounded and durable. The default is one repair attempt; a finite
`repair.retries` can raise that limit. A failed repair produces
`TASK_REPAIR_FAILED` and never invokes another repair. A failed post-repair
original attempt also terminates without another recovery round. Repair nodes,
attempts, and outputs use the normal durable engine rows, so a crash during
repair resumes the same recovery phase.

`continueOnFail` is a different choice: it accepts the failure and continues.
Smithers rejects a task that declares both `repair` and `continueOnFail`.

### Quota exhaustion: park, don't burn

When an agent CLI hits a usage limit, `BaseCliAgent` classifies it (pattern-matching the provider's limit banner, extracting `quotaResetAtMs` when the message names a reset time) and the engine treats it as a **non-attempt**: the failure does not consume retry budget, and the run parks in `waiting-quota` instead of grinding its retries to zero against a wall that won't move. The gateway's sweep (or `bunx smthrs supervise`) resumes the run once the reset time elapses. This is the DLQ insight applied to quotas: don't redeliver into a known-dead consumer.

## Attempt history and per-attempt filesystem state

Every attempt is a row in `_smithers_attempts` (`packages/db/src/internal-schema/smithersAttempts.js`), keyed by `(run_id, node_id, iteration, attempt)`, with `state`, timing, `heartbeat_at_ms`, `error_json`, `response_text` - and `jj_pointer`: a version-control pointer to the working-tree state for that attempt. That last column is the agent-specific part. Attempt 1 may have left the repo half-edited; the attempt record knows exactly what the tree looked like, so you can inspect it (`bunx smthrs node`) or roll the workspace back to it:

```bash
bunx smthrs node -r RUN_ID -n implement          # attempts, errors, tool calls
bunx smthrs revert workflow.tsx -r RUN_ID -n implement --attempt 1
bunx smthrs retry-task workflow.tsx -r RUN_ID -n implement   # reset + resume
bunx smthrs retry-task workflow.tsx -r RUN_ID -n implement -d  # reset, resume detached
```

`retry-task` resets the node (and by default its dependents; `--no-deps` to scope it) and resumes the workflow - the manual override when the automatic budget is spent or you've fixed the environment. By default the engine resumes in the foreground; pass `-d`/`--detach` to hand the run to a background engine (like `up -d`) so it survives your shell or a closed output pipe. The dependent set is approximated from attempt order (the DB stores no dependency edges), so `--deps` can also sweep in siblings that started after the target; use `--no-deps` for a strictly single-node reset. `timetravel` combines both: revert filesystem, reset DB state, optionally `--resume`.

### Side effects: the saga-shaped part

Retrying a task that already sent the email is not recovery, it's a duplicate send. Mark it:

```tsx
<Task id="notify" sideEffect={{ idempotent: false, revert: async (ctx) => {/* compensate */} }} ...>
```

On retry after a non-idempotent side-effect executed, Smithers injects an explicit warning into the next attempt's prompt ("previous attempts already ran non-idempotent side effects") and reuses the same `ctx.idempotencyKey`; `revert`/`timetravel` run registered compensation handlers ([saga-style](https://microservices.io/patterns/data/saga.html)) unless you pass `--no-revert`, and replay across unresolved non-idempotent effects is refused without `--force`. See [Recipes → retry policy](/recipes#retry-policy--timeouts).

## What a failed run tells you

The run-level error is the first thing an operator reads, so it carries the diagnosis rather than a pointer to it. When a node exhausts its retries or stalls, the run error names the node, the attempt count, and the real payload from the last failed attempt:

```text
Task failed: probe-author after 4 attempts: rendered prompt is 683304 bytes, over the 500000-byte cap
  Last good checkpoint: frame 118. Resume with: smithers up workflow.tsx --run-id RUN_ID --resume true
  or replay from the checkpoint with: smithers replay workflow.tsx --run-id RUN_ID --frame 118
```

A stalled node reports the livelock instead:

```text
Task stalled: author-diagram failed 3 consecutive attempts with an identical error:
Diagram login-flow changed its planned participant ordering.
```

The pieces are also structured on the error, so gateway and UI consumers read them without parsing prose: `details.nodeId`, `details.attempts`, and (for `TASK_STALLED`) `details.identicalFailures` and `details.signature`; the raw attempt error stays attached as the error's `cause`.

### Resume is offered at the point of failure

Every terminally failed run gets a `details.recovery` block naming the last good checkpoint and the exact commands to act on it, so recovery does not require knowing which frame to fork:

| Field | Meaning |
| --- | --- |
| `recovery.runId` | The failed run to resume or fork from. |
| `recovery.frameNo` | The last committed frame, if one exists. |
| `recovery.checkpointSeq` | The last workspace checkpoint, if one exists. |
| `recovery.resume` | `bunx smthrs up <workflow> --run-id RUN_ID --resume true` |
| `recovery.replay` | `bunx smthrs replay <workflow> --run-id RUN_ID --frame <n>` |

The same commands appear as next-step actions when `bunx smthrs up` reports a failed run, and `bunx smthrs why` prints the checkpoint and both commands for a failed run. See [Time Travel](/capabilities/time-travel) for what fork and replay actually do.

## When the run itself dies

- **Stale runs** - `bunx smthrs supervise -r RUN_ID` (or `--all` for a workspace sweep) polls every 10s and auto-resumes runs whose heartbeat is stale past 30s (`--interval`, `--stale-threshold`, `--max-concurrent 3`, `--dry-run`). Kubernetes-style restart supervision, but resuming from the durable DB position rather than from zero.
- **Cancellation** - `bunx smthrs cancel RUN_ID` safely halts agents and terminates one run; `smithers pause <runId>` lets in-flight tasks finish and parks resumably; `bunx smthrs down` sweeps all active runs (stale-only unless `--force`).
- **The autopsy** - when `up`/`workflow run` reports a failed run, the `post-failure` system workflow launches automatically: it gathers `inspect`/`events`/source, investigates with read-only tools, classifies the failure (`workflow-bug` / `environment` / `agent-flake` / `smithers-bug` / `unknown`), and emits one suggestion with exact commands - behind an approval gate before any bug is reported. Full details: [Post-Failure Autopsies](/guide/post-failure). Opt out with `--no-post-failure` or `SMITHERS_POST_FAILURE=0`.
- **Reporting** - `smithers bug --run RUN_ID` files a report to bug.smithers.sh with the run's workflow name, status, error, and last ~50 events, secrets scrubbed.

## Guarantees and limits

- Attempt history is durable and complete: every attempt, its error, and its filesystem pointer survive process death.
- Retries are **infinite by default**. That is the right default for overnight runs and the wrong one for side-effectful tasks - bound those explicitly.
- Backoff is capped at 5 minutes and **has no jitter**; large synchronized fan-outs can still thundering-herd a provider on recovery.
- Error classification is built in (quota, preflight/auth, heartbeat, timeout, `ENOENT` preconditions, hard size caps). Instead of Temporal-style `nonRetryableErrorTypes`, per-task control is a `retryPolicy.retryable` flag or predicate.
- Stall detection is per node and per iteration, keyed on consecutive identical signatures. An error that alternates between two messages never stalls; bound those tasks with `retries` as well.
- Retries cannot detect a *plausible wrong answer*. That is what `scorers`, review tasks, and approval gates are for - a retry policy is not a quality gate.
- Repair does not synthesize a plan, approve risky changes, constrain paths, or choose an agent automatically. The workflow author declares the repair agent, instructions, output contract, and finite budget.
