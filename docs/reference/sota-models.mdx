### How to choose a tier

The role table is a starting policy, not a claim that every task belongs to one model. [OpenAI's GPT-5.6 release](https://openai.com/index/gpt-5-6/) describes a three-tier family: Sol is the flagship, Terra is balanced, and Luna is the fastest and most affordable. In Smithers, GPT-5.6 does the building and the reviewing: substantial implementation usually runs on Terra, with Sol for the hardest changes and final code review. Orchestration and gating decisions (scope, choosing direction, whether work progresses, whether it is done) run on Claude instead; maintainer experience is that the 5.6 tiers are strong reviewers but poor gatekeepers.

| Situation | Start with | Escalate when |
| --- | --- | --- |
| Trivial, minimal-risk work: tiny scoped edits, mechanical changes, quick research and lookups, high-volume cheap passes | `gpt-5.6-luna` | The work is real implementation or carries risk; hand it to Terra, or to Sol when the change is hard |
| Substantial implementation by default, plus validation, structured checking, and explicitly tool-heavy work | `gpt-5.6-terra` | The change is genuinely hard, ambiguous, or high-stakes; move implementation or review up to Sol |
| The hardest implementation, final code review, novel architecture, or the deepest reasoning | `gpt-5.6-sol` | Sol reports findings; it does not gate. Scope, direction, progress, and done-or-not decisions go to the Claude orchestrator, and human authority goes to a human gate |
| Orchestration and gating: scope, choosing direction, judging progress, deciding whether work is done, approving or denying gates (run at medium reasoning effort) | `claude-opus-4-8` | Escalate to Fable 5 when the call is unusually consequential and you want Anthropic's strongest judgment; use a human gate for decisions that require human authority |
| Planning and design freezes, deliberate premium judgment on orchestration calls, or the no-Codex fallback for Sol-backed review and smart work | `claude-fable-5` | Use the provider's supported fallback (Opus, then Kimi) or a human gate for decisions that require human authority |
| No usable Codex authentication for Codex-backed research, implementation, validation, mid-tier, or tool-heavy work | `claude-sonnet-5` | Use the provider's supported fallback (Kimi) or an explicit Claude-native specialist choice |

Implementation runs on Codex: start substantial work on Terra and escalate to Sol when the change is genuinely hard, ambiguous, or high-stakes. Luna is reserved for trivial, minimal-risk work (tiny scoped edits, mechanical transforms, quick lookups, high-volume cheap passes) and research-style gathering; it should not carry substantial implementation. Orchestration and gating decisions (scope, choosing direction, judging progress, deciding whether something is done, approving or denying gates) never go to GPT-5.6 Sol or Terra: a Claude model holds those seats, Opus 4.8 at medium reasoning effort by default, with Fable 5 for planning and for calls where you deliberately want Anthropic's strongest judgment. Sol and Terra stay valuable inside reviews and validation, where they report findings that the Claude orchestrator weighs. Agent arrays are sequential fallback chains: a later provider is attempted only when an earlier one is unavailable or fails. An explicitly constructed provider agent is a deliberate choice and can run even when Codex is healthy.

```tsx
const orchestrator = new ClaudeCodeAgent({ model: "claude-opus-4-8" });
const planner = new ClaudeCodeAgent({ model: "claude-fable-5" });
const implementer = new CodexAgent({ model: "gpt-5.6-terra" });
const trivialFixer = new CodexAgent({ model: "gpt-5.6-luna", config: { model_reasoning_effort: "medium" } });
const validator = new CodexAgent({ model: "gpt-5.6-terra" });
const reviewer = new CodexAgent({ model: "gpt-5.6-sol" });
const fableFallback = new ClaudeCodeAgent({ model: "claude-fable-5" });
const smartFallbackChain = [reviewer, fableFallback];
```

In current Claude applications and Claude Code behavior, that Fable-to-Opus switching is enabled by default, while API customers must opt in and configure the fallback themselves ([default product behavior and API opt-in](https://support.claude.com/en/articles/15363606-why-claude-switched-models-in-your-conversation-with-fable-5)). ## Update policy

- Only models with exact usable ids confirmed by provider documentation enter the default registry; marketing-only names and previews without usable ids wait.
- Research previews with real availability (e.g. gpt-5.3-codex-spark on ChatGPT Pro) may enter with status sota for their niche, noted in the description.
- No floating aliases (kimi-latest, *-latest). Pin concrete ids so a provider-side model swap cannot bypass this registry.
- Every badge names exactly one model. A new badge holder demotes the old one in the same change.
- Any change to models bumps version by exactly 1 and refreshes updatedAt.
- Deprecated entries keep their replacedBy id for one release so sweeps know what to rewrite, then get deleted.
- Orchestration and gating seats (scope, direction, progress, done-or-not, approve/deny) are Claude-held: Opus 4.8 holds the orchestrator default and Fable 5 holds planning. GPT-5.6 Sol and Terra never hold those roles, and Luna is for trivial, minimal-risk work only.
