### How to choose a tier

The role table is a starting policy, not a claim that every task belongs to one model. As of registry v7 (Claude Opus 5's 2026-07-24 launch), Claude does the building and the gating and GPT-5.6 does the checking. Opus 5 is the default implementer; its launch benchmarks put it ahead of GPT-5.6 Sol on agentic coding (Frontier-Bench v0.1 43.3% vs 34.4%) at lower output cost ($25 vs $30 per million tokens), and it also holds orchestration and gating (scope, choosing direction, whether work progresses, whether it is done). [OpenAI's GPT-5.6 family](https://openai.com/index/gpt-5-6/) keeps the checking seats: Sol for final code review and second opinions, Terra for validation and structured, tool-heavy checking, Luna for trivial cheap passes; maintainer experience is that the 5.6 tiers are strong reviewers but poor gatekeepers.

| Situation | Start with | Escalate when |
| --- | --- | --- |
| Trivial, minimal-risk work: tiny scoped edits, mechanical changes, quick research and lookups, high-volume cheap passes | `gpt-5.6-luna` | The work is real implementation or carries risk; hand it to Opus 5 (or Terra when you deliberately want a Codex-side build lane) |
| Validation, structured checking, and explicitly tool-heavy verification, or a deliberate Codex-side implementation lane | `gpt-5.6-terra` | The check is genuinely hard, ambiguous, or high-stakes; move review up to Sol. Findings feed the Claude orchestrator, which gates |
| Final code review, second opinions on the hardest changes, and the deepest Codex-side reasoning | `gpt-5.6-sol` | Sol reports findings; it does not gate or carry default implementation. Scope, direction, progress, and done-or-not decisions go to the Claude orchestrator, and human authority goes to a human gate |
| Substantial implementation by default, plus orchestration and gating: scope, choosing direction, judging progress, deciding whether work is done, approving or denying gates (gating runs at medium reasoning effort) | `claude-opus-5` | Escalate to Fable 5 for the most ambitious long-horizon builds or when a call is unusually consequential and you want Anthropic's strongest judgment; use a human gate for decisions that require human authority |
| Planning and design freezes, the most ambitious long-horizon builds, deliberate premium judgment on orchestration calls, or the no-Codex fallback for Sol-backed review | `claude-fable-5` | Use the provider's supported fallback (Opus, then Kimi) or a human gate for decisions that require human authority |
| No usable Codex authentication for the Codex-backed checking seats (research, validation, mid-tier, tool-heavy), or a cheap Claude-native build lane behind Opus 5 | `claude-sonnet-5` | Use the provider's supported fallback (Kimi) or an explicit Claude-native specialist choice |

Implementation runs on Claude Opus 5: start substantial work there, escalating to Fable 5 only for the most ambitious, longest-horizon builds. Codex checks the work: Sol takes final code review and second opinions on the hardest changes, Terra takes validation, structured checking, and explicitly tool-heavy verification, and Luna is reserved for trivial, minimal-risk work (tiny scoped edits, mechanical transforms, quick lookups, high-volume cheap passes) and research-style gathering; neither Terra nor Luna should carry substantial implementation now that Opus 5 outbenchmarks Sol on agentic coding at lower cost. Orchestration and gating decisions (scope, choosing direction, judging progress, deciding whether something is done, approving or denying gates) also stay on Claude (Opus 5 at medium reasoning effort by default, Fable 5 for planning and for calls where you deliberately want Anthropic's strongest judgment) and never go to GPT-5.6 Sol or Terra, whose findings feed the Claude orchestrator's decision. Agent arrays are sequential fallback chains: a later provider is attempted only when an earlier one is unavailable or fails. An explicitly constructed provider agent is a deliberate choice and can run even when Codex is healthy.

```tsx
const orchestrator = new ClaudeCodeAgent({ model: "claude-opus-5" });
const planner = new ClaudeCodeAgent({ model: "claude-fable-5" });
const implementer = new CodexAgent({ model: "gpt-5.6-terra" });
const trivialFixer = new CodexAgent({ model: "gpt-5.6-luna", config: { model_reasoning_effort: "medium" } });
const validator = new CodexAgent({ model: "gpt-5.6-terra" });
const reviewer = new CodexAgent({ model: "gpt-5.6-sol" });
const fableFallback = new ClaudeCodeAgent({ model: "claude-fable-5" });
const smartFallbackChain = [reviewer, fableFallback];
```

### Oneshot task routing

Oneshot routes by task shape before anything else (registry v8). A UI-flavored goal (interface, page, component, styling, layout, responsive, animation, theme, dashboard, and similar keywords; the classifier is apps/cli/src/oneshot/classifyOneshotGoal.js) leads with Kimi K3: OpenCode's `kimi-for-coding/k3` seat first, then kimi through the Pi CLI (`pi --provider kimi-coding --model k3`), then the Kimi CLI's `kimi-code/k3`; when no kimi seat is usable the UI chain falls back to Claude Opus 5, then Fable 5, and Codex Sol is only ever the last-resort UI rung. Every other goal, including tedious backend work (migrations, backfills, renames, test burndowns), runs the default chain led by Claude Opus 5 with Codex Sol, Kimi K3, and Fable 5 behind it, and pi's kimi-coding seat closes that chain. Every rung is availability-gated: oneshot selects only from agents detected usable on the machine, an explicit `--model` or `--agent` always overrides classification, and `smithers oneshot --status` reports the goal's taskType and the resolved chain.

Fable 5 is not a Codex tier. Anthropic describes it as a model for ambitious, long, complex knowledge and coding work; developers can use `claude-fable-5` through the Claude API at $10 per million input tokens and $50 per million output tokens. Anthropic's July 1 redeployment restored access globally on Claude Platform, Claude.ai, Claude Code, and Claude Cowork. For Pro, Max, Team, and select Enterprise plans, Anthropic said Fable 5 would be included for up to 50% of weekly usage limits through July 12, 2026 at 11:59:59 PM PT ([promotion details](https://support.claude.com/en/articles/15424964-claude-fable-5-promotional-access)), after which use requires usage credits; standard Enterprise has no included allowance. Anthropic said it would re-enable AWS, Google Cloud, and Microsoft Foundry as quickly as possible, while its current Fable page lists availability through available marketplaces and those cloud platforms, so cloud-provider and account availability should be treated as conditional rather than universal. Its updated safeguards can reroute blocked requests to Opus 4.8 and can false-positive more often during routine coding and debugging. In current Claude applications and Claude Code behavior, that Fable-to-Opus switching is enabled by default, while API customers must opt in and configure the fallback themselves ([default product behavior and API opt-in](https://support.claude.com/en/articles/15363606-why-claude-switched-models-in-your-conversation-with-fable-5)). Treat this as current product behavior, not a permanent provider guarantee. Smithers gives Claude the building and orchestration seats outright: Opus 5 holds the implementer and orchestrator defaults (substantial implementation plus gating, scope, direction, progress, done-or-not) and Fable holds planning and the most ambitious builds, with each backing the other up; Fable also remains the non-Codex fallback for Sol-backed review. Codex-backed research, validation, mid-tier, and tool-heavy checking roles fall back to Sonnet instead, not Fable; the cited sources do not establish a general latency comparison. Automatic fallback pools do not silently run Fable in parallel with a healthy Codex path; an explicit Claude/OpenCode workflow may choose it directly. In Claude Code the model id is `claude-fable-5`; the OpenCode configuration uses the provider-qualified id `anthropic/claude-fable-5`. See [Anthropic's Fable 5 announcement](https://www.anthropic.com/news/claude-fable-5-mythos-5) and [July redeployment update](https://www.anthropic.com/news/redeploying-fable-5).

## Update policy

- Only models with exact usable ids confirmed by provider documentation enter the default registry; marketing-only names and previews without usable ids wait.
- Research previews with real availability (e.g. gpt-5.3-codex-spark on ChatGPT Pro) may enter with status sota for their niche, noted in the description.
- No floating aliases (kimi-latest, *-latest). Pin concrete ids so a provider-side model swap cannot bypass this registry.
- Every badge names exactly one model. A new badge holder demotes the old one in the same change.
- Any change to models bumps version by exactly 1 and refreshes updatedAt.
- Deprecated entries keep their replacedBy id for one release so sweeps know what to rewrite, then get deleted.
- Building and gating seats are Claude-held: Opus 5 is the default implementer and orchestrator (scope, direction, progress, done-or-not, approve/deny) and Fable 5 holds planning. GPT-5.6 keeps the checking seats (Sol reviews, Terra validates), but Sol and Terra never orchestrate, gate, or carry default implementation, and Luna is for trivial, minimal-risk work only.
- Oneshot routing is task-shaped: UI-flavored goals lead with Kimi K3, every other goal leads with Claude Opus 5, and every rung is availability-gated so oneshot only ever selects an agent that is usable on the machine.
